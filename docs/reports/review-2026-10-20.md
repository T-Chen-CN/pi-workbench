## 三、缺陷详情

### F-01 🔴 Monaco 编辑器从不初始化（已实测）

**位置**: `src/components/MonacoEditor.tsx:18`（初始化 effect），`src/components/MonacoEditor.tsx:175`（`!currentFile` 提前返回）

**复现**:
1. 启动应用，打开任意工作区（此时 `currentFile` 为 `null`，组件返回"没有文件打开"占位符，`editorRef` 指向的 div 未渲染）；
2. 点击文件树中的任意文件。

**现象**: 标签栏正确出现，但编辑区始终空白；DOM 中不存在 `.monaco-editor` 元素。已在 `npm run web:dev` 中通过浏览器实测确认。

**根因**: 创建编辑器的 effect 依赖数组为 `[]`，只在组件挂载时执行一次。首次挂载时 `editorRef.current` 为 `null`，effect 提前返回；之后打开文件时 div 才渲染，但 effect 不会重新执行。`monacoRef.current` 永远为 `null`，后续更新内容、监听变更、自动保存等 effect 全部因同样的空值检查而失效。

**修复建议**: 不要在 `!currentFile` 时卸载编辑器容器。保持编辑器容器始终渲染（占位提示作为覆盖层或相邻元素），或在 `currentFile` 变为非空时创建编辑器。建议同时把 `ref` 回调/`useLayoutEffect` 纳入方案，避免依赖首次渲染时序。

### F-02 🔴 Web 开发模式打开工作区整页白屏（已实测）

**位置**: `src/components/TerminalPanel.tsx:35`（`window.electronAPI.onTerminalData`），同类问题见 `:40`、`:57`、`:89`、`:94`、`:100`、`:107`、`:130`、`:147`、`:160`

**复现**: `npm run web:dev` → 浏览器打开 `http://localhost:5173` → 点击"打开项目"。

**现象**: 控制台报 `Uncaught TypeError: Cannot read properties of undefined (reading 'onTerminalData')`；应用没有错误边界，React 卸载整棵树，界面变为空白。

**根因**: 渲染进程的其它模块都通过 `src/api/index.ts` 访问主进程（Web 模式下自动回退到 `mockAPI`），但 `TerminalPanel` 绕过了这层封装，直接访问 `window.electronAPI`。Web 模式下该对象不存在。`TerminalPanel` 在 `App.tsx` 中只要有工作区就会渲染，因此打开项目即崩溃。AGENTS.md 明确把 `npm run web:dev` 列为前端调试方式，该流程目前完全不可用。

**修复建议**:
1. 在 `src/api/index.ts` 的 mock API 中补齐终端接口（返回 `success:false` 或空实现）；
2. `TerminalPanel` 统一通过 `api.terminal*` 调用，并在 UI 中把"终端不可用"作为正常状态展示，而不是抛异常；
3. 顺带为 `App` 增加错误边界，避免任何单组件异常导致整页白屏。

### F-03 🟠 配置 API Key 后聊天页卡死

**位置**: `src/components/ChatPanel.tsx:96`（`setNeedsApiKey(true)` 的第二个分支）；`needsApiKey` 在文件中没有任何 `setNeedsApiKey(false)`。

**复现**: 首次启动（未配置 API Key）→ 聊天区显示 "API Configuration Required" → 在设置面板填写并保存 Key → 保存成功并派发 `api-config-saved`，Agent 实际初始化成功 → 聊天区仍停留在配置提示页。

**根因**: `needsApiKey` 是一次性置位的状态，重新初始化成功后没有清除；渲染函数在 `needsApiKey` 为 `true` 时提前 return。切换工作区也不会重置（组件保持挂载），只有重启应用才能恢复。

**修复建议**: 在每次 `doInit` 开始时 `setNeedsApiKey(false)`，或在初始化成功分支中显式清除。

---

### F-04 🟠 自动保存不会触发

**位置**: `src/components/MonacoEditor.tsx:152`（effect cleanup 中的 `clearTimeout`），相关 effect 从 `:129` 开始

**现象**: 用户输入后停止操作并等待超过 2 秒，文件不会被写入磁盘（脏标记仍在），只有 Ctrl/Cmd+S 能保存。

**根因**: `onDidChangeContent` 回调中先调用 `updateOpenFile` / `markDirty` 修改 `currentFile`，再设置 2 秒的保存定时器。该 effect 的依赖里包含 `currentFile`，因此每次按键都会触发重渲染；React 18/19 对 `useSyncExternalStore`（Zustand）的更新在微任务中刷新，effect cleanup 随后执行并 `clearTimeout` 掉刚刚设置的定时器。新的 effect 只重新订阅，不会重设定时器，停止输入后便永不再保存。

**补充**: 该 effect 在每次按键时还会销毁并重建 Monaco 的内容监听订阅，属于不必要的开销。保存逻辑建议脱离 `currentFile` 依赖：用 ref 保存当前路径，或在 change 回调中直接基于 `useEditorStore.getState()` 取值并独立管理防抖定时器。

**修复建议**: 把防抖定时器的创建移出依赖 `currentFile` 的 effect（例如改为 `useEffect(..., [])` 内基于 store 的订阅），并在卸载/切换文件时主动 flush，而不是无条件 `clearTimeout`。修复 F-01 后必须回归验证本项。

### F-05 🟡 空文件无法打开

**位置**: `src/components/FileExplorer.tsx:147`

**复现**: 用 ✚ 新建文件（内容为 `''`）→ 在文件树中点击该文件。

**现象**: 弹出 "Failed to open file: Failed to read file"。

**根因**: 判断条件写成了 `if (!result.success || !result.content)`，空字符串是合法内容，却被当作失败。

**修复建议**: 改为 `typeof result.content !== 'string'`。

---

### F-06 🟡 关闭脏标签后永久处于"有未保存修改"状态

**位置**: `src/store/editorStore.ts:34`（`removeOpenFile`）

**复现**: 编辑文件 → 点击标签 × → 确认丢弃修改 → 关闭项目 / 切换工作区 / 关闭窗口。

**现象**: 即使没有任何打开的文件，仍会弹出未保存修改确认。

**根因**: `markDirty` 会向 `unsavedChanges` 集合写入路径，但 `removeOpenFile` 只从 `openFiles` 中移除，没有同步删除 `unsavedChanges` 中的记录；`hasDirtyFiles()` 同时检查两者，因此永远为 `true`，直到 `reset()`。

**修复建议**: `removeOpenFile` 中一并从 `unsavedChanges` 删除该路径；`addOpenFile` 重新打开文件时也应清除残留记录。`tests/stores.test.ts` 建议补充"打开→标脏→关闭→hasDirtyFiles 为 false"的用例。

---

### F-07 🟡 文件监听防抖丢失多文件变更事件

**位置**: `electron/main.ts:339`

**现象**: Agent 或外部工具在 300ms 内修改多个文件时，渲染进程只能收到最后一个文件的 `fs:changed`。

**根因**: 防抖实现是"取消上一个定时器 + 覆盖闭包中的 `filename`/`eventType`"，而不是聚合成一组待发送事件。`MonacoEditor` 的外部变更同步按 `payload.path === currentPath` 过滤，因此其它已打开文件的磁盘变更不会被反映（Diff 还原后编辑器也可能继续显示旧内容）。

**修复建议**: 用一个 `Map<string, eventType>` 收集窗口期内的变更，定时器触发时批量发送（或逐条发送）；同时把路径归一化（Windows 下大小写）后比较。

### F-08 🟡 语言选择在重启后被重置

**位置**: `src/App.tsx:47`

**复现**: 设置中切换为 English（`i18nStore` 已通过 `persist` 保存）→ 重启应用。

**现象**: 界面回到中文。

**根因**: `App` 挂载时执行 `if (language !== 'zh') setLanguage('zh')`，覆盖持久化的用户选择。语言选择器实际只在当前会话有效。

**修复建议**: 删除该强制逻辑，或仅在 `localStorage` 中不存在任何历史设置时写入默认值。修复时请结合 F-10 一并调整持久化位置。

---

### F-09 🟡 崩溃重启后 Fleet 任务永久卡在 running

**位置**: `electron/fleet-manager.ts:187`

**复现**: 提交 Fleet 任务 → 任务运行期间强制结束应用 → 重新启动。

**现象**: 任务一直显示"运行中"，既不会重跑也不会失败；`cleanupWorktree` 拒绝 running 状态，用户只能手动取消。

**根因**: 任务状态在启动时直接以数据库内容为准，`pump()` 只调度 `queued`，没有任何恢复逻辑把上次进程遗留的 `running` 任务标记为失败（或重新排队）。`disposeAll` 也不会取消运行中的任务。

**修复建议**: `FleetManager` 初始化时把所有 `running` 任务更新为 `failed`，错误信息注明"应用退出导致任务中断"；如需自动恢复，可改为重新入队（注意避免重复执行副作用）。

### F-10 🟡 语言设置违反便携式架构约束

**位置**: `src/store/i18nStore.ts:25`（`persist` 的 `name: 'pi-workbench-language'`）

**规范依据**: AGENTS.md「文件路径规范（便携式约束）」要求"所有应用数据必须在应用目录内，不得使用系统标准路径"，并将 `app.getPath('userData')` / `appData` 等列为错误做法。

**问题**: `persist` 中间件写入渲染进程 `localStorage`，而 Electron 的 `localStorage` 落在 Chromium 的 profile 目录（`app.getPath('userData')`，Windows 下为 `%APPDATA%\pi-workbench`）。`electron/main.ts` 未调用 `app.setPath('userData', ...)`。由此带来：
- 整体复制/迁移应用目录后语言设置丢失；
- 卸载后系统目录残留数据；
- 与"便携式、自包含"的产品承诺矛盾。

**修复建议**: 语言偏好改走已有的 `app:getSettings` / `app:saveSettings`（`{appDir}/config/settings.json`）；如仍需前端快速读取，可在启动时从主进程同步注入初值。同时建议评估是否需要将整个 `userData` 重定向到应用目录（Chromium 缓存本身也会写入该目录，这一点当前同样与便携式目标存在偏差）。

## 四、通过项与良好实践

- **架构约束**: Agent 运行在主进程；渲染进程通过 `contextBridge` 访问文件系统，`contextIsolation: true`、`nodeIntegration: false`；未发现 Tauri 残留。
- **密钥处理**: API Key 使用 `safeStorage` 加密（`enc:` 前缀），迁移时兼容旧明文；`models.json` 通过环境变量引用 Key，不落盘；日志中未发现 Key 泄漏。

- **测试基础**: 主进程 IPC、AgentManager、插件、Fleet、终端、store 均有覆盖（124 用例），为后续修复提供了回归基础。
