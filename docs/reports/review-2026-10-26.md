## 三、高优先级问题

### P0-1【高危｜安全】会话删除存在路径穿越，可删除应用目录内任意 `.json`

**调用链**

1. `electron/main.ts:2813` 的 `agent:sessions:delete` 只校验了 `workspaceDir`，未校验 `sessionId`，原样传给 `agent.deleteSession(sessionId)`。
2. `pi-bridge/src/agent-manager.ts:2730` 的 `deleteSession` 先 `SessionManager.findById(...)`，随后**无论 `file` 是否存在**都调用 `extrasStore.delete(sessionId)`。
3. `pi-bridge/src/session-extras.ts:47` 的 `pathFor` 直接 `path.join(baseDir, \`${sessionId}.json\`)`，无字符白名单、无包含校验。
4. `session-extras.ts:84` 的 `delete` 对结果执行 `fs.unlink`。

**证据**：baseDir 为 `{appDir}/data/agent/session-extras`（`agent-manager.ts:1025`）。Node 实测：

```text
path.join('C:/app/data/agent/session-extras', '../../../config/settings.json')
→ C:\app\config\settings.json
```

**影响**

- 渲染层传入 `sessionId = "../../../config/settings"` 可删除 `{appDir}/config/settings.json`；继续增加 `../` 可指向用户可写的任意 `.json`，绕过主进程为渲染层设置的「只能写工作区与缓存」边界。
- 传入其他工作区的合法 sessionId 会删除该会话的 sidecar（权限、计划、工具 Diff、分支记录），而会话 JSONL 仍保留，造成跨工作区数据丢失且状态不一致。
- `save` / `load` 共用同一 `pathFor`：越界写/读同样可能，只是内容受 extras 结构约束。

**修复建议**

- 在 `main.ts` 与 `agent-manager` 双层校验 `sessionId`：仅允许 `[A-Za-z0-9._-]{1,128}`，拒绝路径分隔符与 `..`。
- `deleteSession` 调整顺序：`findById` 返回有效文件后，再删除运行时与 sidecar；找不到会话时直接返回失败。
- `SessionExtrasStore` 内部对最终路径做 `path.resolve` + 前缀包含判断，作为最后一道防线。
- 补一条回归测试：恶意 sessionId 不得删除 `{appDir}/config/settings.json`。

### P0-2【中高｜正确性】只读安装目录会导致主进程启动即崩溃

- `electron/draft-store.ts:23` 的构造函数直接 `fs.mkdirSync(rootDir, { recursive: true })`，没有 try/catch。
- `electron/main.ts:354` 在模块求值阶段就创建 `DraftStore`，早于 `app.whenReady()`。
- 专门处理「安装到 Program Files」的 `ensureAppDirWritable`（`main.ts:421`）在 `createWindow()` 之后才执行（`main.ts:600`），来不及提示。

**影响**：安装在不可写目录时，Electron 直接显示主进程未捕获异常，用户看不到可解释的错误，也拿不到重新安装的指引。

**修复建议**：DraftStore 构造函数容错，或延迟到 `whenReady` 后再创建；把可写性探测提前到窗口创建之前。

### P0-3【中｜流程】发布流水线不做类型检查，`vite.config.ts` 不在任何类型检查内

- `.github/workflows/release.yml:57` 打 tag 后只执行 `npm test` 与 `npm run build`。
- `package.json:15` 的 `build` 是 Vite/esbuild + 主进程 tsc + bridge tsc，不会对 `src/` 做 `tsc`。
- `tsconfig.json:24` 把 `tsconfig.node.json` 作为 project reference，但 `tsc --noEmit` 不会构建 reference，因此 `vite.config.ts` 实际从未被类型检查。

**影响**：直接推 tag 发布时，渲染层类型错误或 Vite 配置错误不会被拦截。

**修复建议**：Release 工作流增加 `npm run type-check && npm run lint`；新增 `tsc -p tsconfig.node.json --noEmit` 覆盖 `vite.config.ts` / `vitest.config.ts`。

### P0-4【中｜仅开发态】Vite Agent 桥默认全自动、无鉴权

- `vite.config.ts:180`：`getDefaultPermissionLevel: () => 'auto'`，且没有 `requestApproval` 通道。
- `vite.config.ts:98-442`：15 个 `/__pi/agent/*` 端点直接在本机 Node 进程里运行 `AgentManager`，无 token、无来源校验。

**影响**：`npm run web:dev` 期间，本机任意进程都可以初始化 Agent 并在项目目录执行任意命令。属开发态取舍，但建议至少要求启动时生成的随机 token，或只在显式标志下启用。

**同处的功能缺口**：`vite.config.ts:193` 与 `:207` 的 chat 端点未透传 `images`，Web 调试模式下图片附件被静默丢弃；`/__pi/fetch-models` 代理没有超时（主进程版本有 15s 超时）。

## 四、复杂设计与架构问题

### C-1 ChatPanel 单文件 3547 行，职责严重混合

`src/components/ChatPanel.tsx`（主组件约从 `:555` 开始）同时承担：会话标签与抽屉、流式 trace 缓冲、附件（文件/符号/图片）、图片预处理、斜杠命令、提示模板与技能、计划审批、模型/思考/权限菜单、上下文仪表、用量与预算、排队与 steer、审批卡、会话置顶归档、导出、工具结果查看、滚动与响应式收起。统计：14 个 `useState`、22 个 `useEffect`、20 个 `useCallback`、8 个 `useMemo`、9 个 `useRef`。

文件内已有 `TurnTaskList`、`TurnEditSummary`、`MessageImages`、`ChatMessageRow` 等内部组件，说明拆分路径已经存在。建议拆为：

- `useAgentSession`（初始化、流式、历史、会话切换）
- `Transcript`（虚拟列表 + 消息行 + 滚动）
- `Composer`（输入、附件、斜杠命令、排队）
- `StatusBar`（模型、思考、权限、上下文、用量）
- `SessionMenu` / `SessionDrawer`

### C-2 `electron/main.ts` 2994 行、92 个 IPC handler

同一文件包含窗口生命周期、路径信任、设置迁移、API Key 加解密、Agent 初始化、会话/计划/导出/审批映射、通知、更新器装配。`electron/agent-registry.ts:36` 的 `RegisteredAgent` 把方法声明为全可选，导致主进程出现 **32 处** `typeof agent.xxx !== 'function'` 守卫，而这些方法在唯一的 `AgentManager` 实现中全部存在。

此外 `RegisteredAgent.chat` 的 options 类型缺少 `images`（`electron/agent-registry.ts:36-54`），主进程却通过变量传入（`electron/main.ts:2102`）；因 TypeScript 对变量不做多余属性检查而没有报错，说明这层抽象已经开始漂移。

建议按域拆为 files / workspace / agent / session / update 五个模块，用一个 `withAgent(handler)` 统一「取实例 + 方法存在性 + 错误包装」。

### C-3 `pi-bridge/src/agent-manager.ts` 3236 行

一个类同时负责：环境变量租约、`models.json` 生成、Git Bash PATH 注入、会话事件归一化、审批扩展、计划工具、分支树算法、工具结果分页、Markdown/HTML 导出、用量/设置、会话生命周期、聊天主循环、标题生成。建议至少拆出 `session-export`、`session-runtime`、`model-config` 三个模块；标题生成可独立成服务。

### C-4 Web 调试是第二套后端

`vite.config.ts:98-442` 约 344 行在 Node 里重跑 `AgentManager`，15 个端点对应主进程 92 个通道；端点半常量在 `vite.config.ts:82` 与 `src/api/piAgentAPI.ts:83` 各写一份。已出现能力差距：无审批、无分支、无计划、无工具结果、无导出、图片被丢弃。`src/api/piAgentAPI.ts`（897 行）为每个方法维护 Electron / HTTP 双分支。

建议二选一：裁剪为最小只读子集并明确声明支持范围；或抽成独立 dev 插件、复用端点常量，并补齐 images 与超时。

### C-5 最近工作区同时写两种存储

- `electron/main.ts:354` 创建 `data/workspaces.db`（node:sqlite，带 JSON 回退）。
- `electron/main.ts:1351` 的读取同时合并 `settings.json` 的 `recentWorkspaces` 与 SQLite 的 `listRecent(30)`。
- 打开工作区时 `workspace:init` 记录一次（`main.ts:1407`），随后 `addRecentWorkspace` 又记录一次（`main.ts:1382`）。
- `WorkspaceStore.list()`、`openCount` 在生产代码中无任何消费者，只有测试使用。

E-04 引入 SQLite 的规模理由（应对 Fleet 规模）已随 Fleet 移除而消失；当前只为 10 条最近工作区排序，维护了 150 行存储代码 + 原生模块 + 回退分支。建议收敛到 `settings.json` 单一来源。

### C-6 会话 sidecar 无上限保存完整文件内容

- `pi-bridge/src/session-extras.ts:21` 的 `ToolEditRecord` 保存 `oldContent + newContent` 全文。
- `pi-bridge/src/agent-manager.ts:933`、`:961` 在 `tool_execution_start/end` 回调里用 `readFileSync` 同步读取整文件。
- 每次编辑都把整个 extras JSON 重新序列化落盘（`agent-manager.ts:796`）。

## 六、行为、性能与规范一致性

### P-1 `ChatMessageRow` 的 memo 实际失效

- `ChatPanel.tsx:303` 注释写「memo 保证流式追加只重渲染最后一条」。
- `handleCopyMessage`（`:2379`）、`handleRetryMessage`（`:2389`）、`handleEditMessage`（`:2417`）、`handleApprovePlan`（`:2130`）、`handleRejectPlan`（`:2118`）都是普通函数，每次渲染都换新引用；`onCopy` 又传给所有消息行，导致 `React.memo` 浅比较必定失败。
- ChatPanel 直接订阅整份 conversation（`:572`），`setDraftInput` 每次按键都会生成新对象，叠加上流式 50ms flush，可见消息会反复重渲染。

建议：回调 `useCallback` 化，或让消息行按 `id` 自行订阅 store；拆分时把草稿输入移出消息树的订阅范围。

### P-2 排队消息持久化的全量开销

`ChatPanel.tsx:1376` 订阅整个 chatStore；每次状态变化（含每个字符、每个流式片段）都对所有工作区的 conversation 执行两次 `JSON.stringify` 比较。建议只订阅当前工作区的 pending 字段，由 `addPending/removePending` 显式触发防抖写入。

### P-3 工作区级 ref 在并行会话之间串扰

`ChatPanel.tsx:803` 的 `stoppedRef`、`forceSendRef`、`budgetWarnedRef` 是工作区级 ref，而项目支持同一工作区并行运行多个会话。会话 A 点击停止后 `stoppedRef` 保持到 A 的请求收尾；若此时会话 B 失败，`ChatPanel.tsx:2046` 会把 B 的错误当成「用户主动停止」清掉，B 的排队消息也不会自动发送（`:2077`）。建议按 `conversationKey` 维护 Map，或移入 session store。

### P-4 首页执行会话命令静默失效却提示成功

App 只要存在 workspace 就渲染 CommandPalette（`src/App.tsx:672`）；首页时所有 ChatPanel 的监听因 `active === false` 直接退出（`ChatPanel.tsx:1647`）。用户从首页执行「新建会话 / 会话列表 / 重命名」时事件无人接收，而 `CommandPalette.tsx:236` 仍把结果记为 success。应在首页禁用这些命令，或路由到当前工作区视图。

### P-5 设置保存是读-改-写竞态

`Settings.tsx:172` 的 `persistSettings` 每次先 `api.getSettings()` 再 `api.saveSettings({ ...settings, ...patch })`。快速切换两个设置时，两个异步流程可能都读到旧文件，后写覆盖前写。建议渲染层串行化写队列，或主进程提供 merge 接口。

### P-6 无 selector 的全量订阅

- `MonacoEditor.tsx:109`：`useEditorStore(workspacePath)` 无 selector，每次编辑内容变化都重渲染整个组件与标签。
- `SessionTabs.tsx:33`：订阅整份 `conversations`，任一工作区的草稿/流式输出都会重渲染所有已挂载工作区的标签栏。
- `DiffViewer.tsx:28`：无 selector 订阅 diff store。

### P-7 App 重渲染会连带所有 WorkspaceView

`App.tsx:61` 订阅全局 `streaming`、`errors`、`needsAction`，任一变化都会重新 map 所有工作区；`WorkspaceView` 与 `ChatPanel` 均无 `React.memo`。多工作区时隐藏视图也会跟着渲染。结构上存在明显浪费，实际成本需 profiling。

### P-8 全局 `window` CustomEvent 事件总线

至少 10 个字符串事件跨组件传递：`open-settings`、`open-command-palette`、`workspace-toggle-terminal`、`pi:refresh-files`、`pi:insert-slash`、`attach-selection`、`api-config-saved`、`session-new/list/rename/delete/close`。没有类型约束、注册顺序和生命周期保障，与「Zustand 管理状态」的约定不一致。建议改为 store action 或集中到带类型的事件模块。

### P-9 其他一致性问题

- **终端标题硬编码 zsh**：`TerminalPanel.tsx:230` 在 Windows 上显示 zsh，实际 shell 优先 `ComSpec`（通常是 cmd.exe，`terminal-manager.ts:84`）。

- **计划兜底提示硬编码英文**：`ChatPanel.tsx:2163` 在中文界面也发送 `Execute the plan above step by step.`。
- **字符代替图标**：`translations.ts:520-521` 使用 `✓ / ✗`；`App.tsx:706` 使用文本 `● PI AGENT`。设计系统要求图标统一 lucide、状态点使用样式化 span。

### P-10 测试覆盖缺口

- `WorkspaceView`（多工作区常驻、面板拖拽/收起、焦点管理）与 App 级关闭提醒没有直接测试。

## 十、未验证 / 需真机确认的推测

### 12.2 第二轮实施前的待办（按优先级）

> **状态更新**：本节记录第二轮开始前的清单；除文末「方案落地记录」列出的残余项外，均已在第二轮完成。

以下问题在首轮未修改；前五项建议优先处理。

**P1 可靠性 / 性能**

1. **会话 sidecar 无上限、同步读写** — `pi-bridge/src/session-extras.ts` 对每次 write/edit 保存修改前后全文；`pi-bridge/src/agent-manager.ts` 在工具事件回调中同步读取大文件，并把整个 extras JSON 重新序列化落盘。1MB 文件反复编辑可能产生上百 MB sidecar，下次打开会话整体 `JSON.parse`，同步读还会阻塞承载 PTY 与流式输出的主进程。建议加单文件 / 单会话上限，超限只保存 diff 摘要，读取改异步或按需。
2. **ChatPanel 跨会话 ref 串扰** — `src/components/ChatPanel.tsx` 的 `stoppedRef`、`forceSendRef`、`budgetWarnedRef` 是工作区级 ref。同一工作区并行运行两个会话时，停止会话 A 后，会话 B 的失败会被误判为“用户停止”，B 的排队消息也不会自动发送。建议按 `conversationKey` 维护 Map，或移入 session store。
3. **ChatPanel 渲染开销** — 组件订阅整份 conversation，`handleCopyMessage` 等回调未 memo，导致消息行的 `React.memo` 失效；排队消息持久化在每次 store 变化（含每个字符、每个流式片段）时对所有工作区执行两次 `JSON.stringify`。建议回调 `useCallback` 化、按会话字段订阅、仅对 pending 变化做序列化。
4. **最近工作区双存储** — `electron/main.ts` 同时写 `config/settings.json` 与 `data/workspaces.db`，`workspace:init` 与 `addRecentWorkspace` 各记录一次打开；`WorkspaceStore.list()` / `openCount` 没有生产消费者。需决定保留哪一份（建议只留 `settings.json`），再删除 SQLite 分支与死字段。
5. **Web 调试桥自动放行** — `vite.config.ts` 在 `npm run web:dev` 时默认 `auto` 权限且无 token，本机任意进程都可驱动 Agent 执行命令。建议加启动随机 token，或限制为只读子集。（图片透传与模型代理超时已在本轮修复。）

**P2 加固 / 可维护性**

6. **渲染进程 sandbox** — `BrowserWindow` 仍未显式开启 `sandbox: true`；preload 仅使用 contextBridge / ipcRenderer / webUtils，具备开启条件，但需要一次真机回归。
7. **`@types/node` 升级** — 当前为 20，运行时为 Node 24；升级后可删除 `electron/workspace-store.ts` 手写的 `node:sqlite` 类型 shim。
8. **测试缺口** — `WorkspaceView`（多工作区常驻、面板拖拽/收起、焦点）、App 级关闭提醒、`UpdateDialog`、`UpdateStatusIndicator`、`ErrorBoundary`、`DialogHost` 没有直接测试。
9. **超大文件拆分** — ChatPanel 约 3530 行、`electron/main.ts` 约 2880 行 / 87 个 IPC、`agent-manager.ts` 约 3240 行。建议按会话/输入区/消息区，以及 files/workspace/agent/update 域拆分；同时收紧 `RegisteredAgent` 的可选接口，移除 32 处永不触发的 `typeof agent.*` 守卫。
10. **重复实现收敛** — 虚拟列表样板 4 处、还原逻辑 2 处、路径 basename/join 约 9 处、`react-markdown` 与 `marked` 两套解析栈、未类型化的 `window` CustomEvent 事件总线。
11. **小项**：
    - `.npmrc` 的 `electron_mirror` 触发 npm 弃用警告；
    - `npm run web:dev` 不会自动构建 `pi-bridge/dist`；

    - `messageHistory` 只写不读、随会话增长；

    - Modal 无焦点陷阱与关闭后焦点恢复；
    - 字体资源约 10.6MB、markdown chunk 启动即加载，存在按需加载与子集化空间。

## 十四、运行期回归与修复（2026-10-26，第三轮）

开发版实际运行时出现 `Agent 初始化失败: __dirname is not defined`。排查确认是第二轮拆分引入的两处“模块位置变化导致路径解析失效”，并已修复：

| 位置 | 问题 | 影响 |
|---|---|---|
| `electron/ipc/agent.ts:111` | 编译后位于 `dist-electron/ipc/`，是 ESM 模块，却直接使用未定义的 `__dirname` | `agent:initialize` 必崩，Agent 完全不可用（日志 `logs/main.log` 可复现） |
| `electron/ipc/settings.ts:73` | `__dirname` 有定义，但只退一级，解析到 `dist-electron/pi-bridge/dist/index.js` | 旧版权限迁移静默失败，`permissionLevel` 落到 `ask`；对旧配置更严格的用户反而变松 |

修复方式：在 `electron/app-paths.ts` 新增 `getBridgeEntryUrl()`，按本模块（与 `main.js` 同处 `dist-electron`）的位置解析 `pi-bridge/dist/index.js`，两处调用改用该函数，不再在子目录里手写相对层级。

验证：

- 新增 `tests/app-paths.test.ts`（解析到仓库根下的 `pi-bridge/dist/index.js`，且不含 `dist-electron` 层级）；
- `type-check`、`lint`、49 个文件 / 504 个用例全部通过；
- 用真实 ESM 加载编译后的 `dist-electron/app-paths.js`，解析结果存在且可导入 `AgentManager`、`derivePermissionLevelFromPolicy`；
- 开发版实际运行中通过 IPC 调用 `agent:initialize`，返回 `success: true`，日志记录 `Pi Agent initialized successfully`，会话列表正常读出。

遗留建议：`agent:initialize` 没有单元测试覆盖，而这类“只在真实 ESM 运行时才触发”的问题进不了 Vitest；建议补一条启动冒烟（真实加载编译产物或启动后自动初始化一次 Agent）。
