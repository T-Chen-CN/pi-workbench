# ADR-008：云端单入口插件与「零本地授权」

- **状态**：**已接受**（2026-11-06，项目所有者在会话中授权代定：「这个你决定就行，如果你要我授权我就给你授权就好」）
- **日期**：2026-11-06

- **相关**：[CLOUD_AGENT §6 铁律 S-02](../requirements/CLOUD_AGENT.md) · [CLOUD_AGENT_DEVICES v2](../requirements/CLOUD_AGENT_DEVICES.md) · [agent-runtime](../agent/agent-runtime.md)

## 背景

v5 的 S-02 写的是「云端 Agent **零本地能力**」，判据是「不实现 ACP、不通告 `fs/*` / `terminal/*`」。这条铁律在只有「对话」一个方向时是准确的。

现在要加两件事：

1. **多设备身份**：多台本地程序连同一个云端 Agent，云端要能识别是哪台。
2. **反向派活**：云端 Agent 要能指挥本地 Agent 干活。

第 2 件事与 S-02 的字面表述冲突。但冲突的其实是**措辞**，不是原则：派活的前提是本地**逐次批准**，云端从未获得「直接读写本地」的能力。

同时，方案形态从「自建 `pi-hub` 独立服务」改为「自写 Hermes 插件，作为本地与云端之间的唯一入口」。

## 决定

### 1. S-02 改口径

> **S-02（新）：云端零本地授权。**
> 云端 Agent 不持有任何本地能力；它只能**发请求**。任何作用于本机的动作（写文件、跑命令、读写工作区）都必须由**本地**在动作发生时授予，且授权可逐次拒绝、可全局关闭、可审计。

判据（可检验）：

- 云端侧不存在任何能直接触达本机文件系统或进程的通道（无 ACP、无反向 shell、无 `fs/*` 通告、无端口监听——S-01 不变）；
- 本地收到云端请求时，默认**拒绝**，只有通过「工作区白名单 + 档位上限 + 逐次审批」三关才执行；
- 派活的档位上限由本地配置决定，云端请求更高档位一律 `refused: permission_ceiling`；
- 本地总开关默认为**关**；关闭后云端连入队请求都被拒（`refused: disabled`）；
- 审批超时、审批通道缺失一律视为拒绝（fail-closed）；
- 结果只回摘要，不回完整 diff / 日志 / 绝对路径。

### 1b. 派活单位是工作区，不是设备

云端派活的目标是**工作区**（受信任目录 + 执行上下文），设备只是承载者。`workspaceId` 是不透明 id，**绝对路径永不出本机**；一个工作区同一时刻只属于一台设备。

### 2. 云端单入口：自写 Hermes 插件

本地与云端之间只保留一条缝：VPS 上的 Hermes 插件 `pi-workbench`（`kind: platform`，与 gateway 同进程）。除 dashboard 外，所有对接（轮次、SSE、审批、会话、任务、配置、媒体）都经它转发。

- 设备身份权威在插件：`device token → deviceId`；客户端自称的 `author` 被覆盖。
- 插件对上游只用文档化接口（loopback HTTP + `API_SERVER_KEY`），**不 import 上游内部模块**。
- 插件不获得任何本地能力——它只是**更外面的一层门**，而门后仍然是本地审批。
- 不做直连兜底：插件不可用时明确报错，不静默降级。
  **v3.6 追加**：连「留给回滚的直连字段」也不保留 —— 客户端的 `apiKey` 字段、直连分支、
  连接页的「服务地址 / API 密钥」输入全部删除。回滚只能靠运维修/降级/停用插件，
  代价是云端功能整体不可用，这是刻意选择：结构上不存在第二条缝。

## 理由

1. **原则不变，只是措辞精确化**：能力授予的位置（本地）和形式（逐次审批）都没变；变的是承认「云端可以发请求」这个早已存在的事实。
2. **单一入口是设备身份成立的前提**：两条缝（全局 `API_SERVER_KEY` + 设备 token）会让「哪台设备做的」永远说不全，且 `approvals.mode` 这类安全写操作任何持钥匙者都能改。
3. **插件比独立服务更省**：少一个常驻服务、少一个 systemd 单元、少一处备份；aiohttp 已是上游依赖；`plugin_data_dir` 提供随 profile 走的数据目录；`plugin doctor` 提供校验。
4. **风险可收敛**：插件与 agent 同进程，所以 token 只存 hash、审计独立落盘、邮箱不存完整命令；而**派活的最终闸门在本地**——即使云端被完全接管，也拿不到超出 `readonly` 的能力。

## 后果

**正面**

- 设备可单台撤销、限权（`chat` / `dispatch` / `admin`）、限速、逐条审计；
- 上游接口变更由插件吸收，本地客户端只认一个地址一个 token；
- 派活能力有明确的失败语义与固定拒绝原因枚举（`disabled` / `permission_ceiling` / `unknown_project` / …）。

**负面 / 代价**

- 插件是单点：它挂了云端就不可用（已接受，无兜底）；
- 插件与 agent 同进程，一个阻塞调用就能拖慢 agent（用异步 sqlite + 逐路由超时缓解）；
- 上游插件 API 是耦合点（用 ≤120 行的 `shim.py` + 版本区间隔离）；
- S-02 的书面承诺从「零能力」变成「零授权」，需要靠测试与审计来证明，而不是靠「我们没有实现」这一事实。

## 替代方案与放弃理由

| 方案 | 放弃理由 |
| --- | --- |
| 保持 S-02 原话，不做派活 | 与需求 D-03 冲突 |
| 云端直连本地（本地开端口 / 反向隧道） | 违反 S-01，且把审批权移到云端 |
| 自建 `pi-hub` 独立服务 + 其余直连 | 两条缝，设备身份只覆盖一半；多一个常驻服务要运维 |
| 把 dashboard 也纳入插件 | WebSocket + 上游自有前端，代理层会长期不可维护 |
