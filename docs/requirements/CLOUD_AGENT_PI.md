## 1. 背景与目标

### 1.1 现状

- 服务器性能与资源有限，**本地机器才是真实的开发环境**：仓库、私有依赖、内网服务、终端、Windows 专有环境都在本地。
- 0.10.0 已把旧的云端 Agent（Hermes 运行时 + 网关插件 + 云端工作区文件能力）整体移除，`pi-bridge` 的 `AgentManager` 与审批 / 计划 / 工作树扩展仍在，是可复用的内核资产。
- 所以不需要"在服务器上再养一个开发环境"，需要的是**调度**。

### 1.2 目标

1. 用户离开电脑时，仍能把开发任务交代出去，并且知道它在推进。
2. 云端 Agent 负责"想和协调"，终端 Agent 负责"动手"，两者的职责不重叠。
3. 用户不需要看执行细节：只要有进度感和可靠的停止按钮（**停止工单** / **停止云端回复**，两件事）。
4. **在任何一台设备上打开都能看到同一份事实**：浏览器（Web）与桌面端看到同样的会话、汇报与指示器状态。

### 1.3 与本项目其它约束的关系

- 历史与导出的唯一真相源是会话记录（JSONL + `parentId` 分支），见 [ADR-003](../decisions/ADR-003-session-record-single-source.md)。云端会话与终端会话各自成立，**互不复制**。
- 权限是安全边界：`readonly` 用 deny 而不是 ask，审批超时与通道缺失一律拒绝（fail-closed）。见 [agent-runtime](../agent/agent-runtime.md)。
- 便携式目录与落盘位置遵循 [paths-and-storage](../agent/paths-and-storage.md)；`data/cloud/` 落在受保护的 `data/` 之下，无需改 `PROTECTED_TOP_LEVEL`（只有新增**顶层**目录才要改）。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| **云端 Agent** | 跑在 VPS 上的 Agent 实例。会对话、出方案、派活、跟进、汇报；**没有** `bash` / `edit` / 读用户文件的工具 |
| **终端 Agent** | 跑在用户机器上的常驻 Agent（复用 `AgentManager`）。真正读写文件、跑命令、跑测试 |
| **Web 客户端** | 云端自带的网页：登录、设备管理、生成配对码，以及**完整会话交互**（聊天 / 确认方案 / 停止）。与桌面端共用同一份云端状态 |
| **工单（task）** | 派活的最小单位。自包含、有状态机、只投原设备、可取消 |
| **工作单元（work unit）** | 一个方案下的目标，**持有一个 worktree**；可被多个工单串行推进（后者承接前者的改动），直到收敛为一次提交 |
| **方案（plan）** | 云端的自然语言方案，含目标设备 / 仓库 / 分支。用户确认后成为授权范围 |
| **授权粒度** | 一次确认 = 授权该方案范围内的派活；换设备、换仓库、明显加码需重新确认 |
| **outbox** | 云端为每台设备 / 每个客户端维护的待投递队列（单调 `seq`），对端 `ack` 后清除 |
| **配对码** | Web 生成的 **6 位一次性数字码**（5 分钟有效），用来把一台桌面端或终端设备接入云端 |
| **客户端通道** | 桌面端 / Web 连到云端的那条长连接（收汇报、发消息、同步状态） |
| **设备通道** | 终端 Agent 连到云端的那条长连接（接工单、回流里程碑） |
| **记忆** | 云端从会话里沉淀的结构化要点（事实 / 偏好 / 项目状态 / 已定决策），按相关性注入上下文 |
| **知识库** | 可检索的文档集合（Web 上传或从工单结果沉淀），检索后注入片段 |
| **梦境** | 空闲时后台整理：去重、归纳、把旧对话转成摘要 + 记忆条目，原文归档 |
| **升级链** | 终端 → 云端 → 用户的三级决策上报路径 |
| **事件唤醒** | 工单状态或终端状态发生变化时，服务端往云端会话投一条 custom message（`customType: 'task-event'`），触发云端跑一轮；云端**不轮询也不阻塞** |

## 3. 核心模型

### 3.1 三个角色

| 角色 | 在哪 | 有仓库 | 能干什么 | 不能干什么 |
| --- | --- | --- | --- | --- |
| 用户 | 桌面端 / 浏览器 | — | 提需求、定设备与仓库、确认方案、回答升级问题、停止工单 | 查看执行细节（不需要） |
| 云端 Agent | VPS 常驻 | ❌ | 对话、出方案、派活给指定终端、跟进、汇报、被下级问 | 读写文件、`bash`、`git`、看代码；替终端放权 |
| 终端 Agent | 每台机器常驻 | ✅ | 读文件、改代码、跑命令、跑测试（与本地会话同一套能力，**不做路径级硬限制**） | 跨设备调度；自己扩权 |

**前提**：device agent 跑在终端 app 的主进程（新增模块，独立 `AgentManager` 实例 + 独立 `agentDir`，已验证同进程可并存两个实例）。因此 **app 必须常驻托盘**——关掉 app 就等于终端离线：不会再收到新工单，正在跑的工单由服务端判 `cancelled`（`device-offline`）并汇报。

**模型配置不隔离（刻意）**：device agent 与用户会话**共用同一份本地模型配置和 API Key**——`acquireProviderEnv()`（`pi-bridge/src/environment.ts:24`）是**模块级引用计数**：任一实例 `initialize()` 都会把 Key 写进 `process.env`（**后 initialize 者胜**），只有最后一个实例释放时才恢复原值。所以两个 `AgentManager` 拿到的必然是同一个 Key。只有**云端 Agent 用另一份 Key**（存服务器上，AES-256-GCM）。**2026-11-20 实测确认**（V1）：双实例共 140 次模型请求，`Authorization` 头去重后只有后 `initialize` 者的 Key（`KEY-B`）；先初始化的实例 `dispose()`（引用计数 2→1）不还原环境变量，最后一个释放时才精确还原成进程原值。所以不要再指望“每实例一份 Key”，也**不要**用“工单 `agentDir` 写另一个环境变量名”去绕：引用计数归 0 时会被还原成“最后一个写的人”，反而更不可控。

不按实例隔离 Key 是确定的设计，不是待办——**前提是把「工单会话与用户会话必须用同一把 Key」写成硬约束**：给工单单独配一把 Key 会在下一次 `initialize()` 后静默串号，而不是报错。

### 3.2 主流程

```
① 用户提需求
② 用户与云端确认「目标终端 + 仓库 + 分支」        ← 方案的前提，先定
③ 云端出方案 ⇄ 聊到用户认可                       ← 唯一的授权闸门
④ 云端按方案派活（不再问设备、不逐次问）
⑤ 终端独立执行，里程碑回流；桌面端与 Web 只显示"正在干活"
⑥ 云端跟进，必要时追加指令 / 升级请示
⑦ 云端汇报进展与结果
```

### 3.3 两级真相源

| 数据 | 真相源 | 另一方只存 |
| --- | --- | --- |
| 云端会话（需求、方案、工单引用、汇报、请示往来） | 云端（JSONL） | — |
| 终端会话（执行过程每一步） | **终端**（JSONL） | 云端存 `{deviceId, sessionId, commit}` 引用 |

云端**不缓存终端仓库内容**，最多缓存仓库路径与 remote 元信息。

### 3.4 客户端面与通道

```
┌────────────────┐      ┌──────────────────────┐      ┌────────────────┐
│ 浏览器 (Web)   │      │ 桌面端 (Electron)      │      │ 终端 Agent      │
│ 完整客户端     │      │ 完整客户端 + 内置执行器 │      │ （同一台机器）  │
└───────┬────────┘      └──────────┬───────────┘      └───────┬────────┘
        │ HTTPS + client WS        │ HTTPS + client WS          │ HTTPS + device WS
        └──────────────┬───────────┴────────────────────────────┘
                       ▼
              Caddy → pi-cloud.service
```

| 面 | 认什么 | 主要用途 | 是否必需 |
| --- | --- | --- | --- |
| Web | 登录 cookie（单账号） | 首次建账号、登录、设备管理、生成配对码、**完整会话交互**（聊天 / 确认方案 / 停止） | 必需 |
| 桌面端 | token | 日常主入口：**独立的云端会话页面**、内置执行器、模型配置 | 必需 |
| 终端 Agent | **同一个 token**（跑在桌面端同一进程） | 接工单、执行、回流里程碑与请示 | 必需（无它就没有执行能力） |

**一台机器 = 一条设备记录 = 一个 token**。token 不区分“客户端角色”和“设备角色”，而是**两条通道**按用途区分：`/client/ws` 收发会话与状态，`/device/ws` 接工单。同一台机器既聊天又执行，**不需要配两次码**（只有在另一台机器上跑时才需要另一个配对码）。

**桌面端云端页是独立视图**，但从现有导航进入，**保留顶栏与底部状态栏**；不新开窗口、不脱离现有的外壳。**云端页与工作区无关**（单会话是全局的）：页面上不显示“切换工作区”，只有“返回首页”——否则切工作区会把云端页也切走，而云端会话并不属于任何工作区。

**为什么是 WebSocket（一句话）**：它是一条双向长连接，服务端随时能推、客户端随时能发，不需要客户端反复问"有新消息吗"；流式输出、工单状态变化、停止指令都靠它即时送达。

**三端共用一套事件帧**：客户端通道与设备通道都发 `AgentTraceEvent`（`text_delta` / `thinking_delta` / `tool_start` / `tool_update` / `tool_end` / `compaction`）以及状态快照帧。共用的是**帧格式与状态模型**；**渲染各自实现，都不复用现有聊天组件**：桌面端云端页另写轻量渲染（不依赖 `chatStore` / `workspaceStore` / `diffStore` / `panelHost`），Web 用纯 ESM 轻量实现（见 D-19）。

运维硬约束（部署时必须满足）：

- 服务单元设 `LimitNOFILE=65536`（默认 `ulimit -n` 只有 1024）
- 进程内并发会话上限 8–10，超出排队而不是全放
- 证书续期由 Caddy 负责；日志走 journald（`journalctl -u pi-cloud`），建议配 `max-size`

### 4.1 身份与准入（Web 登录 + 配对码）

- **F-01** 首次部署后打开 `https://tchen-xiaoxiao.com` → 若无账号，进入「创建管理员账号」（只允许创建一次，创建后该入口关闭）。**这是唯一的自助入口**，之后所有接入都必须先登录。创建动作必须**原子**（文件不存在才创建，例如 `open(..., 'wx')`），否则两个并发请求可以各建一个账号。
- **F-02** 登录：单账号 + 密码。密码只存 `scrypt`（或 argon2id）哈希 + 随机 salt；会话用 `HttpOnly; Secure; SameSite=Lax` 的 cookie；连续失败按来源限速（5 次 / 5 分钟）。`/v1/pair` 与登录用**同一套限速器**（见 F-05）。
- **F-03** Web 设备管理页：设备清单（名称、平台、工作区清单、最后活跃、在线状态）、**生成配对码**、解绑。一台机器一条记录。
- **F-04** 配对码：**6 位纯数字、一次性、5 分钟有效**（`2026-11-21 决定：就用 6 位数字`），只在生成时显示一次（刷新即失效）；云端只存哈希，不落明文，不进日志。
  6 位码的搜索空间（10^6）靠**配套限制**抹平：5 分钟 TTL + 一次性（CAS 写 `used_at`）+ 每来源 5 次 / 5 分钟 + 全局失败熔断 + 所有失败同一错误码（F-05）。**残余风险仍需记着**：配对换到的 token 能开 `/client/ws` 读整条云端会话（对话 / 仓库路径 / diff），所以限速与熔断是这条设计的**必选部分**，不是优化项。
- **F-05** 配对：在桌面端填「服务器地址（默认 `tchen-xiaoxiao.com`）+ 配对码」→ `POST /v1/pair` → 返回 `{deviceId, token}`；桌面端同时上报工作区清单。一次配对，客户端与执行器共用这个 token，**不需配两次**。配对码二次使用一律失败（CAS 写 `used_at`）。
  `/v1/pair` 必须限速（每来源 5 次 / 5 分钟 + 全局失败熔断），且**所有失败返回同一个错误码**，不透露“码是否存在 / 是否过期”。
  未配对时，云端页显示空状态引导：① 打开 `https://tchen-xiaoxiao.com` 登录 → ② 生成配对码 → ③ 填回这里（带服务器地址输入与“测试连接”）。
- **F-06** Token 存储：云端只存 `SHA-256(token + salt)`，**不存明文**；桌面端与终端把明文用 `safeStorage` 加密后落盘。
- **F-07** 多设备：不设单设备限制。设备清单是**唯一事实源**，Web 与桌面端展示同一份。
- **F-08** 解绑：Web 删除哈希 → 该端重连返回 401 → 提示"已被云端移除"并停止重试。
- **F-09** 工作区清单上报：桌面端上报本机**已登记且未删除**的工作区（绝对路径 + remote + 默认分支；非 git 目录只报路径），**不上报文件内容**。派活可选任意一个，不要求当时已打开。**非 git 目录不接受派活**（没有 worktree 就没有隔离，见 G10）。

### 4.2 云端 Agent 配置

- **F-10** 桌面端与 Web 都提供「云端 Agent 配置」入口（模型、baseURL、API Key）。两端写的是**同一份云端配置**，不是两份。
- **F-11** 配置经控制面推送到云端；云端 **AES-256-GCM 加密 at rest**，密钥来自服务器环境变量。
- **F-12** 日志、错误信息、异常堆栈里一律脱敏；UI 只显示掩码（末 4 位）。
- **F-13** 云端配置与本地配置**互不影响**（可以是不同模型）；可覆盖、可轮换。**轮换排队到轮次边界生效**（当前轮 `done` / `cancelled` 后才重建运行时），并回报"新配置将在下一轮生效"——不能直接热替换：`initialize()` 会拆掉所有会话运行时，进行中的轮次会被打断。

### 4.3 方案与授权

- **F-14** 方案是自然语言，**不强制结构化 UI**；但方案必须显式写明：目标设备、仓库、分支、要做什么、怎么算完成。
- **F-15** **目标终端先定**：设备离线、或该设备上没有这个仓库 → 云端必须当场告知用户，**禁止静默换设备**。**派新工单只给在线设备**：离线设备在派活列表里标灰，`dispatch_task` 直接拒绝；设备上线后可在**已确认的方案范围内**继续派，不需要重新确认设备。
- **F-16** 授权按方案粒度：用户确认后，云端可自主派活（含同一方案内连派多个工单），**不逐次请示**。
- **F-17** 超出已确认方案（换设备 / 换仓库 / 明显加码 / 新增目标）→ 云端必须重新征求确认。该约束由**服务端强制**（G9），不能只写在提示词里。
- **F-18** 方案确认动作落进云端会话记录（谁在何时确认了什么），作为后续派活的授权凭据。

### 4.4 工单

- **F-19** 工单**自包含**：终端是另一个模型实例，看不到用户与云端的对话。

  ```
  workUnitId                      工作单元；终端据此复用同一个 worktree（F-19a）
  deviceId                        已锁定，来自方案
  repo / workspace / baseBranch
  背景                            为什么做
  目标 + 验收标准                  怎么算完成
  改动范围预期                     沟通用：大概动哪些地方（不是执行约束）
  禁止事项                         如：不许 force push、不许 push 远端
  产出要求                         摘要 + 变更清单 + 测试结果 + diff（上限）
  是否提交                        由云端按工作单元判定（F-19a）；开 PR 由方案决定
  ```

  「改动范围预期」是**沟通工具**：让你提前知道大概动哪里，不是给执行加锁。超出它不会被阻断，但必须在改动清单里点名（F-36）。工单跑在独立 worktree 里，仓库内的改动碰不到你的工作区；仓库外的绝对路径由 G8 挡住（G7 / G8 / D-20）。**「禁止事项」不再只靠提示词**：单元 worktree 里装 `pre-push` hook 拦推送，G8 的命令级拒绝清单拦 `curl|sh` / 工作树外 `rm -rf`（D-32）—— 因为工单会读仓库里的任意内容，提示词挡不住注入。

- **F-19a** **工作单元（work unit）与工作树**：一个方案的目标可以拆成**多个**工作单元（按设备 / 仓库 / 目标划分，与 F-22 的多设备派活一致），**每个工作单元持有一个 worktree**。同一工作单元的多个工单（包括“未提交 → 后续工单继续推进”）**串行共用同一个 worktree**，改动累积。**是否提交由云端判断**：
  - 判定提交 → 提交，并在汇报里给分支与 commit；
  - 判定不提交 → 必须在会话里说明原因，并派后续工单继续推进，**直到该工作单元收敛为一次提交**（或用户明确放弃）；
  - **绑定方式是 `cloud:<unitId>` 合成 id，不是工单的 sessionId**（G12）：工单会话自身不 `bind`（它用 `createSession(worktreePath)` 直接建在工作树里）；守卫需要的“工作树根”由 `AgentConfig.resolveSessionRoot` 从 device agent 台账给。同时满足三个要求：`boundSessionCount > 0` → `cleanupOrphans` 不收；Git 视图能看见并有 diff 入口；**一个单元只占一行计数**（不会因连派 5 张工单就显示“使用中（5 个会话）”）。
  - **回收时机（v3.3 改写）**：**干净就自动回收，脏才手动**。
    - 触发点：工单进终态（`done` / `failed` / `cancelled` / `interrupted` / `expired`）时，由**云端**判断
      “该 `unitId` 已无其他非终态工单”（队列信息只有云端有），满足则下发 `close_unit`；终端执行
      `release('cloud:<unitId>')`。
    - 回收结果按现有的 `release()` 三态：脏树保留（`removed: false`）、干净且无新提交则删工作树与分支、
      有提交则只删目录并保留 `pi/*` 分支（commit 存活）。**顺序必须严格是“先判干净、再删”**，
      `release()` 自身拒绝删脏树，是第二道保险。
    - **脏树**：不删、不自动回滚，只在汇报与状态栏点名路径，等用户处理完再手动“结束工作单元”。
    - **不自动 release 的例外只剩两点**：① 树不干净；② 该单元还有后续工单在排队/待派（此时删树会让下一张
      工单从 base 重开、丢掉上一张的 commit）。
    - **人工入口仍然必须有**（Git 视图 / 云端页“结束工作单元”）：给脏树、给用户主动放弃、给自动判定漏掉的单元兜底。
    - **兜底扫描**：设备启动时对“云端已标收敛、本地还有台账”的单元补一次回收，覆盖进程被杀/断线那一瞬漏掉的。

- **F-20** 状态机：

  ```
  queued ──assign──▶ assigned ──accept──▶ running ──▶ done
    │                  │                   │    └──▶ failed
    │                  └──▶ rejected       ├──▶ waiting_human ──▶ running
    └──(TTL 到期)──────▶ expired            └──▶ cancelled
  ```

- **F-21** 可靠性：
  - 单设备**并发 1**；多设备可并行。同一设备的多个 `queued` 工单按**入队顺序（FIFO）**依次执行。
  - 重投**只投原设备**，以 `idempotencyKey` 去重；终端先落 `received` 再开工。
  - 取消必须**真 abort** 当前轮，不是只停推流。
  - 终端重连后**先拉服务端状态**：若本地认为还在跑、服务端已 `cancelled` → 本地标取消、**不续跑**，已改的文件留在 worktree（F-19a）；禁止靠本地台账自行续跑。
  - **设备离线 → 工单直接 `cancelled`（reason `device-offline`）**：离线判定沿用 F-46（心跳 25 s，空闲 60 s 判离线）。服务端立即落终态、清掉该工单在 outbox 里的待投递项，往云端会话投一条事件并**向用户汇报**（设备离线、停在哪一步、已改哪些文件）；**不排队、不自动续跑**。
  - `queued` 只覆盖“服务端已生成工单、终端尚未 ack”的短暂窗口：窗口内（60 s）设备离线同样 `cancelled`；超时未 ack 则变 `expired` 并汇报。
  - **终态优先级：服务端先落终态者胜。** 用户从托盘退出时，终端**先发 `interrupted` 再断连**；服务端收到即按 `interrupted` 收尾，不再走离线判定。若服务端已经先判 `cancelled(device-offline)`（进程被杀 / 断网），后到的 `interrupted` 只作附注：**不覆盖终态、不二次汇报**（否则 F-51 的“退出应用”与“异常掉线”两行会在同一张工单上打架）。
- **F-22** 多设备是"方案里选谁"，不是自动路由；同一方案可拆多个工单派到不同设备（例如前端一台、后端一台）。

### 4.5 执行与升级链

```
终端 Agent ──决定不了──▶ 云端 Agent ──决定不了──▶ 用户
     ▲                        ▲                     │
     └──────── 答复下传 ───────┴────── 用户决定 ──────┘
```

- **F-23** 终端可向云端提问并**阻塞等待**：device agent 提供一个 `ask_cloud(question)` 自定义工具（`execute(..., signal)`），发一条 `task:question` 帧后 await 答复；云端答复或超时才继续。超时 / 断线则进入 `waiting_human` 并**停手等**，禁止自行猜测继续改文件。**该工具必须监呼 `signal`**：`cancel` 到达时阻塞中的 await 要立即被抛断，不能挂着不响应（否则 F-21“取消必须真 abort”与 F-25 超时都会失效）。
- **F-24** 云端回答不了 → 向用户请示；拿到答复后**继续推进 / 继续派活**，不需要用户重拍方案。
- **F-25** 每一级都有超时；超时一律 fail-closed（不放行、不默认同意）。`waiting_human` 超时（2 小时）后工单直接变 **`failed`**，汇报原因写“等待用户决定超时”，不自动续跑。
- **F-26** 请示与答复全部落进两边的会话记录，可回溯。

**事件唤醒（替代阻塞等待）**：云端不提供任何阻塞型工具，推进完全靠事件；事件用 SDK 的 **custom message** 投递，**不伪装成用户消息**（§3.6）。

```
云端调 dispatch_task → 本轮结束，立即回到可对话状态
终端状态变化（assigned / 里程碑 / 阻塞 / 完成 / 失败 / 取消）
  → 服务端 sendCustomMessage({customType:'task-event', ...}, {triggerTurn:true, deliverAs})
  → 触发云端跑一轮：读事件 → 必要时 get_task 查快照 → 汇报或继续
```

| 事件到达时云端在干什么 | `deliverAs` | 效果 |
| --- | --- | --- |
| 空闲 | —（`triggerTurn: true`） | `_startRun({ messageType: 'custom' })` 直接开一轮 |
| 正在跑一轮 | `followUp` | 排到本轮之后，**不打断**本轮（压缩、工具调用都不受影响） |
| 用户插话 | `steer` | 注入当前轮，模型在同一步内看到 |

约束：

1. 事件消息用 `customType: 'task-event'` 落盘（这就是“origin”），**不得冒充用户授权**：方案确认、扩权、改变目标只能由用户发出。**这是结构性的**——落盘是 `CustomMessageEntry` 而非 user 消息，模型不会把事件当作用户发言（A-31）。
2. 只在“有意义”的节点投递（接单 / 首个改动 / 测试完成 / 阻塞 / 完成 / 失败 / **取消（含设备离线）**），不是每个工具调用都发。
3. `get_task(taskId)` 必须返回**实时快照**（读服务端当前状态，不缓存），否则回答“现在到哪了”会过时。
4. 本期**不做**工具级停滞检测与主动轮询（见 §7.2 P2 与 BACKLOG）：终端某个工具卡死时云端不会自己发现，只能靠终端断线（L1）或用户手动停止。
5. **一轮只跑一次**：轮次进行中到达的事件用 `deliverAs: 'followUp'` 排队并节流合并（同工单 ≥2 s、跨工单汇总成一条），本轮结束后自动接上一轮；**不允许并发调 `chat()`**（会被直接拒绝）。用户插话走 `steer`，不新开轮次（G11）。**不要自己写队列**：排队的语义在 `sendCustomMessage` / `steer` / `followUp` 里已经成立。

### 4.6 可见性与停止（桌面端 + Web 一致）

| 元素 | 内容 | 位置 |
| --- | --- | --- |
| 任务指示器 | 单工单：设备名 · 标题 · 状态 · 已耗时；多工单：`2 个工单执行中 · 最近：T-007 构建中 03:12`（点开列全部） | 桌面端底部状态栏 + Web 顶栏 |
| 云端会话消息流 | 云端的自然语言汇报（里程碑、阻塞、完成、需要决定） | 桌面端云端页（保留顶栏与底部状态栏）+ Web 会话页 |
| 结果汇报 | 摘要 + 变更清单 + 测试结果 + 引用（commit / diff 位置） | 同上 |
| 停止控制 | **两个按钮，含义不同**：“停止工单”（下发 `cancel`，“影响终端）/ “停止回复”（abort 云端本轮，不影响终端） | 桌面端状态栏 + 会话页 / Web |

- **F-27** 两个入口看的是**同一份数据**：指示器状态与会话都来自服务端快照 + 增量事件，不各自维护本地状态。
- **F-28** **不提供**终端执行过程的查看入口：不显示执行会话、不显示工具调用列表、不显示逐条 trace。云端会话与汇报本身是可见的（那是"协调"不是"执行"）。
- **F-29** 终端会话记录**仍然保留在本地**（排障、审计、结果引用需要），只是没有 UI 入口；用户想了解细节只能通过云端 Agent 转述。记录落在 device agent 自己的 `data/cloud/agent/sessions`，与用户会话目录物理隔离，所以“没有入口”是结构性的，不靠过滤；清理沿用 O-03（不自动清理），排障直接看磁盘。
- **F-30** 停止：状态栏 / Web 的停止按钮 → 云端下发 `cancel` → 终端真 abort。UI 依次显示“正在停止 → 已停止”。设备已离线时工单已被判 `cancelled（device-offline）`，停止按钮置灰并显示“设备离线，工单已取消”，不再发 `cancel`。
- **F-30a** **停止云端回复**：云端自己跑一轮时（读事件、组织汇报），会话页与桌面端提供“停止回复” → 服务端 abort 云端本轮（`AgentManager.abort`），已产出内容保留，会话立即回到可对话。**与“停止工单”是两个不同动作，UI 必须分开**：停止工单影响终端，停止回复只影响云端这一轮。
- **F-31** 停止的后果必须明说：**已改动的文件保留在工单 worktree（不回滚）**，工单标 `cancelled`，云端汇报“停在第几步、改了哪些文件”；被停止的工作单元仍可由后续工单接着做（F-19a）。
- **F-32** 托盘角标可显示运行中工单数（P1，可选）；状态栏是桌面端唯一必需入口。

### 4.7 汇报

- **F-33** 主动汇报节点：派单时（派给谁、干什么）· 首个里程碑 · 阻塞或失败 · 完成 · **取消（含设备离线）** · 需要用户决定。里程碑类汇报做节流（同一工单 ≥2 s 合并一次），避免刷屏。
- **F-34** 汇报必须**可验证**：做了什么、改了哪些文件、测了什么、还剩什么、需要用户定什么；给 commit / 测试输出 / diff 位置，禁止只说"已完成"。
- **F-35** **失败由云端在会话里主动说明**（不是只留个红点）：失败在哪一步、错误摘要、已改的文件、建议的下一步；同时在两端状态栏标记「等待决定」，用户回复后继续。
- **F-36** 工单结束必须给**改动清单**（信息，不是拦截）：按「普通 / 注意」分组列出改动文件——`注意`涵盖 `.env*`、依赖锁文件、CI 工作流、发布配置、git hooks 等；同时对 diff 做一次疑似密钥扫描（只报告命中位置，**不打印值**）。越界不阻断，只点名（D-20）。

### 4.8 单会话与长内容维护

- **F-37** 云端**只保留一个唯一会话**：所有需求、方案、工单、汇报、请示都在这一条会话里。**不做会话列表、不做新建 / 切换 / 删除**。
- **F-38** 上下文预算：接近上限时自动压缩（SDK 默认已开：`reserveTokens 16384` / `keepRecentTokens 20000`，可在 `settings.json` 按模型覆盖；**P0**）。**记忆抽取挂 `session_before_compact` 扩展事件**（拿到 `preparation` + 完整 `branchEntries`，压缩尚未发生），见 §3.6；抽取本身属 **P1**，P0 只压缩。原文“SDK 没有压缩前钩子”是错的（v3.2 已修正）——`compaction_start` 是 pi-bridge 转发的 trace 事件，**拿不到 entries**，不能当钩子用。
- **F-39** **记忆**（**P1**）：结构化条目（事实 / 偏好 / 项目状态 / 已定决策 / 待办），带来源与时间；按相关性注入上下文；用户可在 Web 查看并手工纠正（纠正优先于自动抽取）。
- **F-40** **知识库**（P2）：可检索文档集合（Web 上传 + 从工单结果沉淀），检索后只注入命中片段，不整篇塞进上下文。
- **F-41** **梦境**（P1）：无活跃工单且空闲 ≥30 分钟时后台整理 —— 去重、归纳、把旧对话转成摘要 + 记忆条目、原文归档。整理结果写进会话（可见、可回溯），不静默改事实。
- **F-42** 会话 JSONL 是**唯一真相源**；记忆、知识库、摘要都是**派生索引**，任何时候可重建。

### 4.9 传输与可靠性

**定案：控制面 REST + 数据面 WebSocket（客户端通道 + 设备通道）。**

| 面 | 用途 | 形式 |
| --- | --- | --- |
| 控制面 | Web 登录、配对换 token、下发云端配置、上报仓库清单、拉设备清单、解绑、拉会话历史 | HTTPS + JSON |
| 客户端通道 | 桌面端 / Web：会话事件、汇报、指示器状态、发消息、停止 | `/client/ws` |
| 设备通道 | 终端：工单生命周期、里程碑、请示 / 答复、心跳 | `/device/ws` |

- **F-43** 所有通道都由客户端**主动出站反连**云端（NAT 后不开放端口）。
- **F-44** 云端为每条通道维护 outbox：单调 `seq`，对端 `ack(seq)` 后删除；重连发 `resume(lastAckSeq)` 按序补投 —— 保证工单、取消、汇报不丢。**必须有上限与 TTL**：客户端通道（浏览器标签关了很久）的 outbox 超过上限（建议 2000 条 / 24 h）就丢弃旧增量并在 `resume` 时回 `snapshot` 优先（F-49 已支持），否则 59 GB 磁盘会被拖满；设备通道的待投递项在工单进终态时立即清除（F-21）。
- **F-45** 事件帧沿用 `AgentTraceEvent`，**不复刻旧的 `/v1/runs`**。真实成员（`pi-bridge/src/types.ts:76`）：`text_delta` / `thinking_delta` / **`thinking_redacted`** / `tool_start` / `tool_update` / `tool_end` / **`retry_start` / `retry_end`** / **`compaction_start` / `compaction_end`** / **`plan_submitted` / `plan_updated`**。注意 `compaction` 是**历史 part 类型**，不是流式事件名。
- **F-46** 心跳 25 s；空闲 60 s 判定断线；重连指数退避 + 抖动（1 s → 30 s 封顶）。
- **F-47** **不维护旧客户端兼容**：协议随服务端版本走，不匹配直接拒绝并提示"客户端需更新"；不写版本协商矩阵。SSE 降级留 P2。

### 4.10 多端同步与恢复

- **F-48** 服务端是**唯一状态源**：会话消息、指示器状态、设备状态都由服务端产出，客户端不各自推断。
- **F-49** 每条事件带单调 `seq`；客户端连上后先拿 `snapshot`（当前指示器状态 + 未闭合工单 + 最近 N 条消息），再拿 `sinceSeq` 之后的增量。
- **F-50** 同一时刻多端在线：都收到同样事件，状态一致；不要求"只有一个客户端"。
- **F-51** **关闭客户端与退出应用是两件事**：

  | 动作 | 执行器 | 工单 | 视图 |
  | --- | --- | --- | --- |
  | 关闭浏览器标签 / Web 页 | 不受影响 | 继续跑 | 重开拉快照 |
  | 关闭桌面端**窗口**（X，收托盘） | **还在跑** | 继续跑 | 重开拉快照 |
  | **退出应用**（托盘菜单退出） | 停止 | 正在运行的工单标 `interrupted`，云端汇报“你退出了应用” | — |
  | **异常掉线**（崩溃 / 断网 / 关机） | 停止 | 服务端在离线判定后把工单标 `cancelled`（`device-offline`）并汇报，不排队等待重连 | 重开后拉快照 |

  客户端重开后拉快照恢复视图，并在会话里看到一条**离线期汇报**（"你离开期间：工单 X 完成 / 失败 / 等待决定"）。退出与掉线撞在同一张工单上时，按 **F-21 的终态优先级**（先落终态者胜、后到的只作附注）收尾。
- **F-52** 已读 / 未读：服务端记录最后已读 `seq`，P1 细化（P0 只保证"能看到"）。

### 4.11 数据与落盘

| 位置 | 内容 |
| --- | --- |
| 云端 `/var/lib/pi-cloud/` | `accounts.json`（密码哈希）、`devices.json`（token 哈希 + 仓库清单）、`sessions/*.jsonl`（唯一会话）、`tasks.json`、`outbox/`、`memory/`、`kb/`、`config.enc`（AES-256-GCM）；`workspace/` 与 `agent/` 是云端 `AgentManager.initialize()` 必需的 `workspaceDir` / `agentDir`（会话目录在 `agent/sessions`） |
| 终端与桌面端 `data/cloud/` | **同一个进程、同一个目录**，不是两套存储：`identity.json`（加密 token + `deviceId` + 服务器地址）、`workspaces.json`（仓库清单缓存）、`tasks.json`（工单本地状态 + `idempotencyKey` 台账）、`units.json`（`unitId → worktree path` + `cloud:<unitId>` 绑定 id）；`agent/` 为 device agent 的独立 `agentDir`（`models.json` + `settings.json` + `sessions/`） |
| 终端会话目录 | 执行过程会话落在 `data/cloud/agent/sessions`（device agent 独立 `agentDir`），不进入用户会话目录 |

- 落盘一律走原子写：主进程用 `electron/atomic-json.ts`，`pi-bridge` 侧用它自己的 `pi-bridge/src/atomic-json.ts`（**两份同语义实现，不要跨包 import**）；**不要自己 `writeFile` 覆盖**。
- `data/cloud/` 在受保护的 `data/` 下（`PROTECTED_TOP_LEVEL = config / data / logs / cache`，实际定义在 `scripts/lib/installer-manifest.js:11`）——**不需要也不要**改它。
- ⚠️ 新目录叫 `data/cloud/`，与 0.10.0 首启清理删掉的 `data/cloud-agent/` 名字相近：实现时不要写错路径，也不要把它加进 legacy 清理名单（`electron/legacy-cleanup.ts:38`，那会把新数据删掉）。
- **device agent 的模型配置必须由主进程同步**：`agentDir` 里的 `models.json` / `settings.json` 由 `AgentManager.initialize({ apiConfig })` 生成（Key 不落盘，只写 `$PI_WORKBENCH_API_KEY`）。所以 device agent 的 `initialize()` 要用**用户当前生效的 `apiConfig`**，并在用户改模型配置后重新 `initialize()`——它会重建所有会话运行时，所以只能在**无工单运行**时做（同 F-13 的轮次边界规则）。

### 4.12 部署与运维（P2，最终必须有）

- **F-53** 一份可照着做的部署手册：首次部署（Node、Caddy 片段、systemd 单元、`StateDirectory`、`LimitNOFILE`）、升级流程、回滚、备份（`/var/lib/pi-cloud` + 证书目录）、日志查看与轮转。

## 6. 已确认的决策

| # | 决策 | 理由 / 后果 |
| --- | --- | --- |
| D-01 | 服务器上**不跑开发**：不 clone、不装依赖、不放仓库 | 服务器资源有限；本地才是真实开发环境 |
| D-02 | **工单级委派**，不做工具级远程代发 | 工具级代发要把云端循环挂在本机返回值上：延迟高、断线后状态半死、可靠性最难；工单级只需工单状态机 |
| D-03 | 云端 Agent **没有** `fs` / `bash` / `git` 工具 | 它没有仓库；给了只会变成"在服务器上瞎搞"。工具白名单写死 |
| D-04 | 授权按**方案粒度**，不逐次确认 | 用户要的是"方案认可后它自己干"，逐次确认等于没有自治 |
| D-05 | 目标设备与仓库在**方案阶段**锁定 | 派活时的设备选择是多余的决策；也让"要派到哪"可在方案里被用户直接看到 |
| D-06 | 多设备**不做自动路由** | 路由算法在没有明确收益的情况下增加不确定性；方案里显式指定更可预期 |
| D-07 | **不显示**终端执行会话，只留状态栏 + 停止 | 用户明确表示不需要看过程；黑盒 + 可靠中断反而更符合使用方式 |
| D-08 | 终端会话仍然本地留档 | 排障、审计、汇报引用都需要；"不展示"不等于"不记录" |
| D-09 | 云端配置由**客户端上传** | 不需要在服务器上手工改文件；也让 Key 永远不写进仓库或部署脚本 |
| D-10 | 数据面选 **WebSocket**（控制面 REST） | 需要双向推送 + outbox ack + 游标续传；SSE + POST 会把一条逻辑连接拆成两条腿 |
| D-11 | **修订**：桌面端与 Web 都是**完整客户端**；云端是桌面端的**独立页面** | 入口从首页按钮进入，页面保留顶栏（返回首页）与底部状态栏，不脱离现有外壳；**云端是全局视图，不随工作区切换**（顶栏不放“切换工作区”）。Web 可交互（聊天 / 确认方案 / 停止）。不做手机原生端 |
| D-12 | 本期**不做日常助理** | 先把开发闭环跑通；助理工具集是另一条产品线 |
| D-13 | 部署形态：Node 24 + Caddy 反代 + systemd | 服务只监听 `127.0.0.1:8787`，TLS 与 WS 升级全部交给反代；不需要进程内碰证书 |
| D-14 | 公网**只用 IPv4**（`43.160.211.128`） | 换 IP 后 v4/v6 质量相当（p50 均 54 ms），IPv6 保留但不作为依赖；客户端保持默认双栈选路，不写任何 v6 专有代码 |
| D-15 | 进程内并发上限按内存余量定 | 实测 140 MB 基线 + ~1 MB/会话。单会话模型下云端只有 1 个会话，这条约束实际只约束 device 通道数与工具并发；超出排队，失败降级为可读错误 |
| D-16 | **一个域名 = 一个用户（单账号）** | 不做多租户、不做团队协作；因此不做租户隔离，但仍需登录（域名不是秘密，证书透明日志里全是） |
| D-17 | 云端**只有一个会话**，长内容靠记忆 / 知识库 / 梦境维护 | 用户明确要求；省掉会话管理与切换，也避免"事实散落在多个会话里"；代价是压缩与记忆必须做对 |
| D-18 | **不维护旧客户端兼容** | 旧客户端没有这个功能，直接不维护；协议随服务端走，不匹配即拒绝 |
| D-19 | 三端共用**事件帧**，**渲染各自实现且都不复用现有聊天组件** | 帧格式与状态模型统一，桌面端与 Web 显示同一份会话与指示器。现有 `ChatMessageRow` 依赖 `chatStore` / `workspaceStore` / `diffStore` / `panelHost` / `i18n`，搬到云端页等于再写一套 store。所以：桌面端云端页另写轻量渲染，Web 用纯 ESM 轻量实现；P1 若要合并，先解决 Web 端无构建链的问题 |
| D-20 | 终端工单**不做路径级硬限制**（只留越界写守卫 G8） | 本地 Agent 与用户直接对话时的能力一致：能读改任意文件，因为开发确实需要（`.env` 加变量、CI 改步骤、lock 跟依赖走）。**不做宣称“完全隔离”的路径限制**：它可被 `bash` 绕过，只增加摩擦不增加安全；保留 G8 的越界写守卫（拒绝工作树外绝对路径），定位是**挡误伤与注入的主流路径，不是安全边界**。隔离由 **G7 独立 worktree** 负责，可见性由**改动清单 + 不自动 push** 负责。**注意**：Agent 工具层**没有**“工作区外不可写”这条边界（它只存在于 IPC 文件接口），所以工单能力事实上等同本机 Agent；**2026-11-20 决定：配对页不做风险确认入口**，风险只在本文件写明；**2026-11-21 补充**：命令级拒绝清单 + 单元 worktree 的 `pre-push` hook 作为成本极低的纵深防御（D-32） |
| D-21 | 云端**不提供阻塞型工具**，推进靠事件唤醒 | 阻塞工具会把模型卡在工具调用里：你插话要排队或打断、长工单每 30 s 空转烧 token。事件唤醒下云端派完就回到可对话状态，只在有变化时跑一轮 |
| D-22 | **一机一 token，双通道** | 同一台机器既是客户端又是执行器，没必要配两次码；token 不分角色，`/client/ws` 与 `/device/ws` 按用途区分。另一台机器才需要新的配对码 |
| D-23 | **不设 token 上限、不做成本计量** | 用户明确不要限额配置；上下文控制靠压缩与模型档位（`models.json`），不靠预算门。代价：长会话会持续烧钱，自己盯 |
| D-24 | 工单会话用**独立 `agentDir`**（`data/cloud/agent`） | 与用户会话目录物理隔离：`listSessions` 天然看不到，不需要 `origin` 过滤（G5 取消）；代价是工单会话没有任何 UI 入口与清理入口，排障看磁盘（F-29 / O-03） |
| D-25 | 服务端**允许新增 `ws` 依赖**（2026-11-20 批准） | 全项目唯一新增运行时依赖；Node 内置 `WebSocket` 只是客户端，服务端必须 `ws`。不加就只能回到 SSE + POST，会推翻 D-10 |
| D-26 | Web 端**零 XSS 渲染口径**（2026-11-20 决定） | 手写 markdown 渲染器 + 会话 cookie 是最现实的注入面：**一律用 `textContent` 拼接，不用 `innerHTML` 插模型输出**；只做代码块 / 行内代码 / 列表 / 粗体 / 标题，不做代码高亮与 HTML 透传 |
| D-27 | **不做开机自启**（2026-11-20 决定） | 不是首要考虑的事；代偿是 F-15“只给在线设备派新工单”：app 没启动 = 设备离线 = 不会给新活；已派工单在离线判定后直接 `cancelled（device-offline）` 并汇报（F-21） |
| D-28 | 部署：**本地构建 + rsync 产物**（2026-11-20 决定） | 本地构建 `apps/cloud` 与 `packages/agent-core` → rsync 到 `/opt/pi-cloud` → 服务器 `npm ci --omit=dev`。服务器**不 clone 服务代码仓库、不跑构建**（D-01 的“服务器不放仓库”指用户仓库） |
| D-29 | 云端 Agent 的**交互能力对齐本地**（工具能力仍按 D-03） | P0：停止本轮（F-30a）、插话（`steer`，A-30）；P1：重试 / 编辑重发（`rewindToLastUser` 现成）。工具集仍只有派活类 6 个，不给 `fs` / `bash` / `git` |
| D-30 | 工单事件用 **SDK custom message** 投递，不伪装用户消息（2026-11-21） | `sendCustomMessage({customType:'task-event'}, {triggerTurn, deliverAs})` 落盘为 `CustomMessageEntry`，与 user 消息不同型 → A-31“事件不冒充授权”是结构性的，不靠提示词；也顺带解决“轮次进行中合并事件”：`deliverAs: 'followUp'` 是 SDK 原生排队 |
| D-31 | 工作单元用**合成绑定 id `cloud:<unitId>`**（2026-11-21） | 一个单元只占一条 `session-git.json` 绑定（不是每张工单一条），`cleanupOrphans` 不收、Git 视图能展示、`release()` 一次回收；**不改 `session-git.json` 结构**（`loadSessionGit` 是白名单加载，加字段要同步改 loader，没必要） |
| D-32 | 纵深防御：**命令级拒绝清单 + 单元 worktree 的 `pre-push` hook**（2026-11-21） | D-20 接受“写守卫可被 bash 绕过”，但工单会读仓库里的任意内容（README / issue / 依赖脚本），注入→任意命令执行无任何阻拦。两者成本都接近 0：守卫挂在已有的 `tool_call` 钩子上，`pre-push` 把“不许 push”从提示词变成硬拦 |
| D-33 | **不重命名 `pi-bridge`**，`apps/cloud` 直接依赖它的产物（2026-11-21） | 改名要同步 `electron/app-paths.ts:32`、`package.json` 的 `workspaces` 与 electron-builder `files`、`vite.config.ts:161`、`tsconfig.node.json`、`docs/agent/agent-runtime.md`，还会牵动 asar/NSIS 清单与 132 个测试；收益只是命名。所以只补导出（`sendCustomMessage` / 轮次结束信号 / `session_before_compact` 接入），不做目录重构 |
| D-34 | 配对码**就用 6 位纯数字**（2026-11-21 用户确定） | 输码成本优先，不换高熵码。爆破面（10^6）靠配套限制抹平：5 分钟 TTL + 一次性 + 每来源 5 次 / 5 分钟 + 全局熔断 + 失败同一错误码（F-04 / F-05）；**这些限制是这条设计的必选部分**，实现时不得省。残余风险（token 可读整条会话）写在本表，不再在 UI 加确认入口 |

### 6.1 明确不采用

- 服务器上跑 Pi 开发会话（旧版"云端工作区"）。
- 使用旧 `/v1/runs` 协议与网关插件（插件仓库已删除）。
- 逐工具往返代发、工具级租约、工具级审计。
- 强制结构化方案编辑器。
- 云端多会话 / 会话列表 / 会话切换。
- 手机原生客户端、多租户、团队协作。

## 9. 与旧 Hermes 实现的差异

| 维度 | 旧（0.8.0–0.9.1） | 本方案 |
| --- | --- | --- |
| 运行时 | 第三方 Hermes | Pi Agent（`AgentManager` 复用） |
| 服务器上的开发能力 | 有（云端工作区、文件读写） | **没有**，只有派活与协调类工具 |
| 派活语义 | 任务 + 租约 + 网关插件转发 | 工单级委派，云端直连终端 WS |
| 协议 | 自研 `/v1/runs` + SSE | 控制面 REST + 客户端通道 + 设备通道（WS），帧用 `AgentTraceEvent` |

| 用户可见性 | 内嵌控制台，可看执行细节 | 桌面端 + Web 看会话与指示器，**不看执行过程** |
| 会话模型 | 多会话 | **单会话** + 记忆 / 知识库 / 梦境维护长内容 |
| 网关插件 | 独立 Python 仓库 | **不存在** |
