> **什么时候读**：动 `apps/cloud`、终端派活（device agent）、云端会话、工单状态机之前
> **什么时候要改**：角色边界、通道形态、工单语义、可见性或验收场景变化时

**日期**：2026-11-19
**范围**：云端 Agent 的调度闭环 —— 提需求、定目标终端与仓库、出方案、确认、派活、跟进、汇报、停止；外加 Web 管理面（鉴权、设备管理、配对码、查看）

## 1. 背景与目标

### 1.1 现状

- 服务器性能与资源有限，**本地机器才是真实的开发环境**：仓库、私有依赖、内网服务、终端、Windows 专有环境都在本地。
- 0.10.0 已把旧的云端 Agent（Hermes 运行时 + 网关插件 + 云端工作区文件能力）整体移除，`pi-bridge` 的 `AgentManager` 与审批 / 计划 / 工作树扩展仍在，是可复用的内核资产。
- 所以不需要"在服务器上再养一个开发环境"，需要的是**调度**。

### 1.2 目标

1. 用户离开电脑时，仍能把开发任务交代出去，并且知道它在推进。
2. 云端 Agent 负责"想和协调"，终端 Agent 负责"动手"，两者的职责不重叠。
3. 用户不需要看执行细节：只要有进度感和一个可靠的停止按钮。
4. **在任何一台设备上打开都能看到同一份事实**：浏览器（Web）与桌面端看到同样的会话、汇报与指示器状态。

### 1.3 与本项目其它约束的关系

- 历史与导出的唯一真相源是会话记录（JSONL + `parentId` 分支），见 [ADR-003](../decisions/ADR-003-session-record-single-source.md)。云端会话与终端会话各自成立，**互不复制**。
- 权限是安全边界：`readonly` 用 deny 而不是 ask，审批超时与通道缺失一律拒绝（fail-closed）。见 [agent-runtime](../agent/agent-runtime.md)。
- 便携式目录与落盘位置遵循 [paths-and-storage](../agent/paths-and-storage.md)；新增运行时目录必须同步 `PROTECTED_TOP_LEVEL`。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| **云端 Agent** | 跑在 VPS 上的 Agent 实例。会对话、出方案、派活、跟进、汇报；**没有** `bash` / `edit` / 读用户文件的工具 |
| **终端 Agent** | 跑在用户机器上的常驻 Agent（复用 `AgentManager`）。真正读写文件、跑命令、跑测试 |
| **Web 管理面** | 云端自带的网页：登录、设备管理、生成配对码、查看会话与汇报。不是 Agent 客户端，不提供额外的执行能力 |
| **工单（task）** | 派活的最小单位。自包含、有状态机、只投原设备、可取消 |
| **方案（plan）** | 云端的自然语言方案，含目标设备 / 仓库 / 分支。用户确认后成为授权范围 |
| **授权粒度** | 一次确认 = 授权该方案范围内的派活；换设备、换仓库、明显加码需重新确认 |
| **outbox** | 云端为每台设备 / 每个客户端维护的待投递队列（单调 `seq`），对端 `ack` 后清除 |
| **配对码** | Web 生成的一次性短码，用来把一台桌面端或终端设备接入云端 |
| **客户端通道** | 桌面端 / Web 连到云端的那条长连接（收汇报、发消息、同步状态） |
| **设备通道** | 终端 Agent 连到云端的那条长连接（接工单、回流里程碑） |
| **记忆** | 云端从会话里沉淀的结构化要点（事实 / 偏好 / 项目状态 / 已定决策），按相关性注入上下文 |
| **知识库** | 可检索的文档集合（Web 上传或从工单结果沉淀），检索后注入片段 |
| **梦境** | 空闲时后台整理：去重、归纳、把旧对话转成摘要 + 记忆条目，原文归档 |
| **升级链** | 终端 → 云端 → 用户的三级决策上报路径 |

## 3. 核心模型

### 3.1 三个角色

| 角色 | 在哪 | 有仓库 | 能干什么 | 不能干什么 |
| --- | --- | --- | --- | --- |
| 用户 | 桌面端 / 浏览器 | — | 提需求、定设备与仓库、确认方案、回答升级问题、停止工单 | 查看执行细节（不需要） |
| 云端 Agent | VPS 常驻 | ❌ | 对话、出方案、派活给指定终端、跟进、汇报、被下级问 | 读写文件、`bash`、`git`、看代码；替终端放权 |
| 终端 Agent | 每台机器常驻 | ✅ | 读文件、改代码、跑命令、跑测试（与本地会话同一套能力，**不做路径级硬限制**） | 跨设备调度；自己扩权 |

**前提**：device agent 跑在终端 app 的主进程（新增模块，独立 `AgentManager` 实例 + 独立 `agentDir`，已验证同进程可并存两个实例）。因此 **app 必须常驻托盘**——关掉 app 就等于终端离线，工单进 `queued` 等它回来。

### 3.2 主流程

```
① 用户提需求
② 用户与云端确认「目标终端 + 仓库 + 分支」        ← 方案的前提，先定
③ 云端出方案 ⇄ 聊到用户认可                       ← 唯一的授权闸门
④ 云端按方案派活（不再问设备、不逐次问）
⑤ 终端独立执行，里程碑回流；桌面端与 Web 只显示"正在干活"
⑥ 云端跟进，必要时追加指令 / 升级请示
⑦ 云端汇报进展与结果
```

### 3.3 两级真相源

| 数据 | 真相源 | 另一方只存 |
| --- | --- | --- |
| 云端会话（需求、方案、工单引用、汇报、请示往来） | 云端（JSONL） | — |
| 终端会话（执行过程每一步） | **终端**（JSONL） | 云端存 `{deviceId, sessionId, commit}` 引用 |

云端**不缓存终端仓库内容**，最多缓存仓库路径与 remote 元信息。

### 3.4 三个客户端面与三条通道

```
┌──────────────┐        ┌──────────────┐        ┌──────────────┐
│ 浏览器 (Web) │        │ 桌面端 (Electron) │    │ 终端 Agent    │
│ 登录/设备/查看│        │ 聊天/状态栏/配置 │    │ 执行工单      │
└──────┬───────┘        └──────┬───────┘        └──────┬───────┘
       │ HTTPS + client WS     │ HTTPS + client WS     │ HTTPS + device WS
       └───────────────┬───────┴───────────────────────┘
                       ▼
              Caddy → pi-cloud.service
```

| 面 | 认什么 | 主要用途 | 是否必需 |
| --- | --- | --- | --- |
| Web 管理面 | 登录 cookie（单账号） | 首次建账号、登录、设备管理、生成配对码、查看会话与汇报 | 必需（配对入口） |
| 桌面端 | token | 日常主入口：聊天、状态栏、云端配置上传 | 必需 |
| 终端 Agent | token | 接工单、执行、回流里程碑与请示 | 必需（无它就没有执行能力） |

**为什么是 WebSocket（一句话）**：它是一条双向长连接，服务端随时能推、客户端随时能发，不需要客户端反复问"有新消息吗"；流式输出、工单状态变化、停止指令都靠它即时送达。

**三端共用一套事件帧**：客户端通道与设备通道都发 `AgentTraceEvent`（`text_delta` / `thinking_delta` / `tool_start` / `tool_update` / `tool_end` / `compaction`）以及状态快照帧。共用的是**帧格式与状态模型**；渲染各自实现（桌面端复用现有聊天组件，Web 用轻量只读渲染，见 D-19）。

### 3.5 部署形态（定稿）与服务器基线

```
│ 云端配置推送        │ ───────────────▶ │   ├─ /          → Web 管理面（静态）     │
└────────────────────┘                 │   ├─ /v1/*      → 127.0.0.1:8787（REST）│
                                       │   ├─ /client/ws → 桌面端 / Web 通道     │
                                       │   └─ /device/ws → 终端设备通道          │
浏览器 ────────────────────────────────▶ │ pi-cloud.service（Node 24 · systemd）  │
                                       └───────────────────────────────────────┘
                                                     ▲
                                       WSS 反连（终端主动出站）
                                                     │
                                       ┌─────────────┴─────────────┐

                                       │ AgentManager，有仓库权限） │
                                       └───────────────────────────┘
```

实测基线（2026-11-19，详见 [服务器可行性报告](../reports/cloud-server-feasibility-2026-11-19.md)）：

| 项 | 值 |
| --- | --- |
| 公网 | **只用 IPv4** `43.160.211.128`（原 IP 已被墙，更换后恢复）；IPv6 保留但不作依赖 |
| 域名 / 证书 | `tchen-xiaoxiao.com`，Caddy 自动签发并续期 Let's Encrypt（`tls-alpn-01` 已验证） |
| 机器 | Ubuntu 26.04 · 2 vCPU · 3.7 GB 内存 · 59 GB 磁盘（已用 12%） |
| 运行时 | Node 24.22.3 + `@earendil-works/pi-coding-agent` 1.3.0（`npm install` 41 s / 155 MB） |
| 常驻服务 | `caddy.service` + `pi-cloud.service`，systemd 托管；`kill -9` 后 3 s 内自愈 |
| 端口 | 对外仅 80 / 443；服务只监听 `127.0.0.1`（SSH 仅限源） |
| 延迟 | WS 往返 **p50 ≈ 54 ms**（国内 ↔ 新加坡）；TLS 1.3 握手 150–200 ms |
| 传输能力 | WS 空闲 90 s 不断线、20 并发 0 失败、SSE 无缓冲 |
| 内存基线 | 空进程 140 MB；空会话 ≈ 1 MB/个 → 8–10 并发会话安全 |

运维硬约束（部署时必须满足）：

- 服务单元设 `LimitNOFILE=65536`（默认 `ulimit -n` 只有 1024）
- 进程内并发会话上限 8–10，超出排队而不是全放
- 证书续期由 Caddy 负责；日志走 journald（`journalctl -u pi-cloud`），建议配 `max-size`
- 公网 IP 变更 → 同步改 DNS A 记录（被墙时表现为**静默超时**，不是快速失败）
- 客户端连接超时 8 s，错误分级：`无网络` / `解析失败` / `连接超时` / `服务端错误`
- `PermitRootLogin` 改 `prohibit-password`，服务用专用非 root 账号运行

### 4.1 身份与准入（Web 登录 + 配对码）

- **F-01** 首次部署后打开 `https://tchen-xiaoxiao.com` → 若无账号，进入「创建管理员账号」（只允许创建一次，创建后该入口关闭）。**这是唯一的自助入口**，之后所有接入都必须先登录。
- **F-02** 登录：单账号 + 密码。密码只存 `scrypt`（或 argon2id）哈希 + 随机 salt；会话用 `HttpOnly; Secure; SameSite=Lax` 的 cookie；连续失败按来源限速（5 次 / 5 分钟）。
- **F-03** Web 设备管理页：设备清单（名称、平台、仓库清单、最后活跃、在线状态）、**生成配对码**、解绑。桌面端（`desktop` 角色）与终端（`device` 角色）在同一张表里，用角色区分。
- **F-04** 配对码：**一次性、5 分钟有效、6 位数字或 8 位短码**，只在生成时显示一次（刷新即失效）；云端只存哈希，不落明文，不进日志。
- **F-05** 配对：桌面端 / 终端填写「服务器地址（默认 `tchen-xiaoxiao.com`）+ 配对码」→ `POST /v1/pair` → 返回 `{id, role, token}`；终端同时上报仓库清单。配对码二次使用一律失败。
- **F-06** Token 存储：云端只存 `SHA-256(token + salt)`，**不存明文**；桌面端与终端把明文用 `safeStorage` 加密后落盘。
- **F-07** 多设备：不设单设备限制。设备清单是**唯一事实源**，Web 与桌面端展示同一份。
- **F-08** 解绑：Web 删除哈希 → 该端重连返回 401 → 提示"已被云端移除"并停止重试。
- **F-09** 仓库清单上报：终端上报本机可派活的仓库（绝对路径 + remote + 默认分支），**不上报文件内容**。

### 4.2 云端 Agent 配置

- **F-10** 桌面端与 Web 都能改「云端 Agent」配置：模型、baseURL、API Key（日常走桌面端；Web 作为备用入口）。
- **F-11** 配置经控制面推送到云端；云端 **AES-256-GCM 加密 at rest**，密钥来自服务器环境变量。
- **F-12** 日志、错误信息、异常堆栈里一律脱敏；UI 只显示掩码（末 4 位）。
- **F-13** 云端配置与本地配置**互不影响**（可以是不同模型）；可覆盖、可轮换。**轮换排队到轮次边界生效**（当前轮 `done` / `cancelled` 后才重建运行时），并回报"新配置将在下一轮生效"——不能直接热替换：`initialize()` 会拆掉所有会话运行时，进行中的轮次会被打断。

### 4.3 方案与授权

- **F-14** 方案是自然语言，**不强制结构化 UI**；但方案必须显式写明：目标设备、仓库、分支、要做什么、怎么算完成。
- **F-15** **目标终端先定**：设备离线、或该设备上没有这个仓库 → 云端必须当场告知用户，**禁止静默换设备**。
- **F-16** 授权按方案粒度：用户确认后，云端可自主派活（含同一方案内连派多个工单），**不逐次请示**。
- **F-17** 超出已确认方案（换设备 / 换仓库 / 明显加码 / 新增目标）→ 云端必须重新征求确认。
- **F-18** 方案确认动作落进云端会话记录（谁在何时确认了什么），作为后续派活的授权凭据。

### 4.4 工单

- **F-19** 工单**自包含**：终端是另一个模型实例，看不到用户与云端的对话。

  ```
  deviceId                        已锁定，来自方案
  repo / workspace / baseBranch
  背景                            为什么做
  目标 + 验收标准                  怎么算完成
  改动范围预期                     沟通用：大概动哪些地方（不是执行约束）
  禁止事项                         如：不许 force push、不许 push 远端
  产出要求                         摘要 + 变更清单 + 测试结果 + diff（上限）
  是否提交 / 开 PR                 执行细节，由方案决定，不写死
  ```

  「改动范围预期」是**沟通工具**：让你提前知道大概动哪里，不是给执行加锁。超出它不会被阻断，但必须在改动清单里点名（F-36）。工单跑在独立 worktree 里，怎么改都碰不到你的工作区（G7 / D-20）。

- **F-20** 状态机：

  ```
  queued ──assign──▶ assigned ──accept──▶ running ──▶ done
    │                  │                   │    └──▶ failed
    │                  └──▶ rejected       ├──▶ waiting_human ──▶ running
    └──(TTL 到期)──────▶ expired            └──▶ cancelled
  ```

- **F-21** 可靠性：
  - 单设备**并发 1**；多设备可并行。
  - 重投**只投原设备**，以 `idempotencyKey` 去重；终端先落 `received` 再开工。
  - 取消必须**真 abort** 当前轮，不是只停推流。
  - 终端离线时工单留在 `queued`，有 TTL，到期变 `expired` 并汇报给用户。
- **F-22** 多设备是"方案里选谁"，不是自动路由；同一方案可拆多个工单派到不同设备（例如前端一台、后端一台）。

### 4.5 执行与升级链

```
终端 Agent ──决定不了──▶ 云端 Agent ──决定不了──▶ 用户
     ▲                        ▲                     │
     └──────── 答复下传 ───────┴────── 用户决定 ──────┘
```

- **F-23** 终端可向云端提问并**阻塞等待**；超时则进入 `waiting_human` 并**停手等**，禁止自行猜测继续改文件。
- **F-24** 云端回答不了 → 向用户请示；拿到答复后**继续推进 / 继续派活**，不需要用户重拍方案。
- **F-25** 每一级都有超时；超时一律 fail-closed（不放行、不默认同意）。
- **F-26** 请示与答复全部落进两边的会话记录，可回溯。

**实现约束（`wait_task`）**：云端只有一个会话，`wait_task` 阻塞期间用户新消息会排队 —— 必须允许用户消息打断（走 SDK 的 `steer`），或改成“快照立即返回 + 工单事件驱动唤醒”。P0 必须二选一并在联调时验收（否则交互上会像卡死）。

### 4.6 可见性与停止（桌面端 + Web 一致）

| 元素 | 内容 | 位置 |
| --- | --- | --- |
| 任务指示器 | 设备名 · 工单标题 · 状态（排队 / 执行中 / 等待决定 / 正在停止 / 已停止）· 已耗时 | 桌面端底部状态栏 + Web 顶栏 |
| 云端会话消息流 | 云端的自然语言汇报（里程碑、阻塞、完成、需要决定） | 桌面端聊天视图 + Web 会话页 |
| 结果汇报 | 摘要 + 变更清单 + 测试结果 + 引用（commit / diff 位置） | 同上 |

- **F-27** 两个入口看的是**同一份数据**：指示器状态与会话都来自服务端快照 + 增量事件，不各自维护本地状态。
- **F-28** **不提供**终端执行过程的查看入口：不显示执行会话、不显示工具调用列表、不显示逐条 trace。云端会话与汇报本身是可见的（那是"协调"不是"执行"）。
- **F-29** 终端会话记录**仍然保留在本地**（排障、审计、结果引用需要），只是没有 UI 入口；用户想了解细节只能通过云端 Agent 转述。
- **F-30** 停止：状态栏 / Web 的停止按钮 → 云端下发 `cancel` → 终端真 abort。UI 依次显示"正在停止 → 已停止"；终端离线时停止请求进 outbox，UI 显示"停止请求已排队"。
- **F-31** 停止的后果必须明说：**已改动的文件保留在工作区（不回滚）**，工单标 `cancelled`，云端汇报"停在第几步、改了哪些文件"。
- **F-32** 托盘角标可显示运行中工单数（P1，可选）；状态栏是桌面端唯一必需入口。

### 4.7 汇报

- **F-33** 主动汇报节点：派单时（派给谁、干什么）· 首个里程碑 · 阻塞或失败 · 完成 · 需要用户决定。里程碑类汇报做节流（同一工单 ≥2 s 合并一次），避免刷屏。
- **F-34** 汇报必须**可验证**：做了什么、改了哪些文件、测了什么、还剩什么、需要用户定什么；给 commit / 测试输出 / diff 位置，禁止只说"已完成"。
- **F-35** **失败由云端在会话里主动说明**（不是只留个红点）：失败在哪一步、错误摘要、已改的文件、建议的下一步；同时在两端状态栏标记「等待决定」，用户回复后继续。
- **F-36** 工单结束必须给**改动清单**（信息，不是拦截）：按「普通 / 注意」分组列出改动文件——`注意`涵盖 `.env*`、依赖锁文件、CI 工作流、发布配置、git hooks 等；同时对 diff 做一次疑似密钥扫描（只报告命中位置，**不打印值**）。越界不阻断，只点名（D-20）。

### 4.8 单会话与长内容维护

- **F-37** 云端**只保留一个唯一会话**：所有需求、方案、工单、汇报、请示都在这一条会话里。**不做会话列表、不做新建 / 切换 / 删除**。
- **F-38** 上下文预算：接近上限时自动压缩（沿用 SDK 的 compaction，阈值可配）；**压缩发生时**（`compaction_start` 事件，此时旧消息仍在）先从会话记录抽取要点写进记忆，避免压缩后丢失决策。SDK 没有“压缩前”钩子，所以必须用这个事件而不是前置拦截。
- **F-39** **记忆**：结构化条目（事实 / 偏好 / 项目状态 / 已定决策 / 待办），带来源与时间；按相关性注入上下文；用户可在 Web 查看并手工纠正（纠正优先于自动抽取）。
- **F-40** **知识库**（P2）：可检索文档集合（Web 上传 + 从工单结果沉淀），检索后只注入命中片段，不整篇塞进上下文。
- **F-41** **梦境**（P1）：无活跃工单且空闲 ≥30 分钟时后台整理 —— 去重、归纳、把旧对话转成摘要 + 记忆条目、原文归档。整理结果写进会话（可见、可回溯），不静默改事实。
- **F-42** 会话 JSONL 是**唯一真相源**；记忆、知识库、摘要都是**派生索引**，任何时候可重建。

### 4.9 传输与可靠性

**定案：控制面 REST + 数据面 WebSocket（客户端通道 + 设备通道）。**

| 面 | 用途 | 形式 |
| --- | --- | --- |
| 控制面 | Web 登录、配对换 token、下发云端配置、上报仓库清单、拉设备清单、解绑、拉会话历史 | HTTPS + JSON |
| 客户端通道 | 桌面端 / Web：会话事件、汇报、指示器状态、发消息、停止 | `/client/ws` |
| 设备通道 | 终端：工单生命周期、里程碑、请示 / 答复、心跳 | `/device/ws` |

- **F-43** 所有通道都由客户端**主动出站反连**云端（NAT 后不开放端口）。
- **F-44** 云端为每条通道维护 outbox：单调 `seq`，对端 `ack(seq)` 后删除；重连发 `resume(lastAckSeq)` 按序补投 —— 保证工单、取消、汇报不丢。
- **F-45** 事件帧沿用 `AgentTraceEvent`（`text_delta` / `thinking_delta` / `tool_start` / `tool_update` / `tool_end` / `compaction`），**不复刻旧的 `/v1/runs`**。
- **F-46** 心跳 25 s；空闲 60 s 判定断线；重连指数退避 + 抖动（1 s → 30 s 封顶）。
- **F-47** **不维护旧客户端兼容**：协议随服务端版本走，不匹配直接拒绝并提示"客户端需更新"；不写版本协商矩阵。SSE 降级留 P2。

### 4.10 多端同步与恢复

- **F-48** 服务端是**唯一状态源**：会话消息、指示器状态、设备状态都由服务端产出，客户端不各自推断。
- **F-49** 每条事件带单调 `seq`；客户端连上后先拿 `snapshot`（当前指示器状态 + 未闭合工单 + 最近 N 条消息），再拿 `sinceSeq` 之后的增量。
- **F-50** 同一时刻多端在线：都收到同样事件，状态一致；不要求"只有一个客户端"。
- **F-51** 应用 / 浏览器关闭不影响云端与工单：重开后拉快照即恢复视图，并在会话里看到一条**离线期汇报**（"你离开期间：工单 X 完成 / 失败 / 等待决定"）。
- **F-52** 已读 / 未读：服务端记录最后已读 `seq`，P1 细化（P0 只保证"能看到"）。

### 4.11 数据与落盘

| 位置 | 内容 |
| --- | --- |
| 云端 `/var/lib/pi-cloud/` | `accounts.json`（密码哈希）、`devices.json`（token 哈希 + 仓库清单）、`sessions/*.jsonl`（唯一会话）、`tasks.json`、`outbox/`、`memory/`、`kb/`、`config.enc`（AES-256-GCM） |
| 终端 `data/cloud/` | 加密 token、`deviceId`、设备清单缓存、工单本地状态（`idempotencyKey` 台账） |
| 桌面端 `data/cloud/` | 加密 token、服务器地址、客户端 `lastAckSeq` |
| 终端会话目录 | 执行过程会话（沿用现有会话管理，不新增目录语义） |

- 落盘一律走 `electron/atomic-json.ts` 的原子写（云端复用同一实现）；**不要自己 `writeFile` 覆盖**。
- 新增运行时目录必须同步 `PROTECTED_TOP_LEVEL`，否则更新会把目录当程序文件删掉。

### 4.12 部署与运维（P2，最终必须有）

- **F-53** 一份可照着做的部署手册：首次部署（Node、Caddy 片段、systemd 单元、`StateDirectory`、`LimitNOFILE`）、升级流程、回滚、备份（`/var/lib/pi-cloud` + 证书目录）、日志查看与轮转。
- **F-54** 健康检查端点 `GET /v1/health`（不鉴权，只返回版本与就绪状态），供 Caddy 与人工巡检使用。
- **F-55** 备份策略：每日打包 `sessions/` `tasks.json` `devices.json` `memory/`，保留 7 天。

## 6. 已确认的决策

| # | 决策 | 理由 / 后果 |
| --- | --- | --- |
| D-01 | 服务器上**不跑开发**：不 clone、不装依赖、不放仓库 | 服务器资源有限；本地才是真实开发环境 |
| D-02 | **工单级委派**，不做工具级远程代发 | 工具级代发要把云端循环挂在本机返回值上：延迟高、断线后状态半死、可靠性最难；工单级只需工单状态机 |
| D-03 | 云端 Agent **没有** `fs` / `bash` / `git` 工具 | 它没有仓库；给了只会变成"在服务器上瞎搞"。工具白名单写死 |
| D-04 | 授权按**方案粒度**，不逐次确认 | 用户要的是"方案认可后它自己干"，逐次确认等于没有自治 |
| D-05 | 目标设备与仓库在**方案阶段**锁定 | 派活时的设备选择是多余的决策；也让"要派到哪"可在方案里被用户直接看到 |
| D-06 | 多设备**不做自动路由** | 路由算法在没有明确收益的情况下增加不确定性；方案里显式指定更可预期 |
| D-07 | **不显示**终端执行会话，只留状态栏 + 停止 | 用户明确表示不需要看过程；黑盒 + 可靠中断反而更符合使用方式 |
| D-08 | 终端会话仍然本地留档 | 排障、审计、汇报引用都需要；"不展示"不等于"不记录" |
| D-09 | 云端配置由**客户端上传** | 不需要在服务器上手工改文件；也让 Key 永远不写进仓库或部署脚本 |
| D-10 | 数据面选 **WebSocket**（控制面 REST） | 需要双向推送 + outbox ack + 游标续传；SSE + POST 会把一条逻辑连接拆成两条腿 |
| D-11 | **修订**：桌面端为主入口，**Web 提供鉴权 / 设备管理 / 查看** | 配对必须有可信的生成入口，纯桌面端无法回答"第一台设备从哪来"；但 Web 不做 Agent 客户端、不做手机原生端（会话查看是只读复用，不增加执行能力） |
| D-12 | 本期**不做日常助理** | 先把开发闭环跑通；助理工具集是另一条产品线 |
| D-13 | 部署形态：Node 24 + Caddy 反代 + systemd | 服务只监听 `127.0.0.1:8787`，TLS 与 WS 升级全部交给反代；不需要进程内碰证书 |
| D-14 | 公网**只用 IPv4**（`43.160.211.128`） | 换 IP 后 v4/v6 质量相当（p50 均 54 ms），IPv6 保留但不作为依赖；客户端保持默认双栈选路，不写任何 v6 专有代码 |
| D-15 | 进程内并发会话上限 8–10 | 按实测内存基线（140 MB + ~1 MB/会话）留出余量；超出排队，失败降级为可读错误 |
| D-16 | **一个域名 = 一个用户（单账号）** | 不做多租户、不做团队协作；因此不做租户隔离，但仍需登录（域名不是秘密，证书透明日志里全是） |
| D-17 | 云端**只有一个会话**，长内容靠记忆 / 知识库 / 梦境维护 | 用户明确要求；省掉会话管理与切换，也避免"事实散落在多个会话里"；代价是压缩与记忆必须做对 |
| D-18 | **不维护旧客户端兼容** | 旧客户端没有这个功能，直接不维护；协议随服务端走，不匹配即拒绝 |
| D-19 | 三端共用**事件帧**（渲染各自实现） | 帧格式与状态模型统一，桌面端与 Web 显示同一份会话与指示器。但**渲染不能共用**：桌面端聊天组件依赖 workspace / chat / panelHost 等 store 与 Electron API，硬搬到云端会把渲染层拖进服务端；Web 用轻量只读渲染，P1 可再抽无依赖的纯展示层 |
| D-20 | 终端工单**不做路径级硬限制** | 本地 Agent 与用户直接对话时的能力一致：能读改任意文件，因为开发确实需要（`.env` 加变量、CI 改步骤、lock 跟依赖走）。硬限制可被 `bash` 绕过，只增加摩擦不增加安全。隔离改由 **G7 独立 worktree**负责，可见性由**改动清单 + 不自动 push** 负责；唯一的硬边界仍是已有的“工作区外不可写”（保证可 review、可回滚） |

### 6.1 明确不采用

- 服务器上跑 Pi 开发会话（旧版"云端工作区"）。
- 使用旧 `/v1/runs` 协议与网关插件（插件仓库已删除）。
- 逐工具往返代发、工具级租约、工具级审计。
- 强制结构化方案编辑器。
- 云端多会话 / 会话列表 / 会话切换。
- 手机原生客户端、多租户、团队协作。

## 9. 与旧 Hermes 实现的差异

| 维度 | 旧（0.8.0–0.9.1） | 本方案 |
| --- | --- | --- |
| 运行时 | 第三方 Hermes | Pi Agent（`AgentManager` 复用） |
| 服务器上的开发能力 | 有（云端工作区、文件读写） | **没有**，只有派活与协调类工具 |
| 派活语义 | 任务 + 租约 + 网关插件转发 | 工单级委派，云端直连终端 WS |
| 协议 | 自研 `/v1/runs` + SSE | 控制面 REST + 客户端通道 + 设备通道（WS），帧用 `AgentTraceEvent` |
| 设备规模 | 单设备并发 1 | 多设备并行，单设备仍并发 1 |
| 用户可见性 | 内嵌控制台，可看执行细节 | 桌面端 + Web 看会话与指示器，**不看执行过程** |
| 会话模型 | 多会话 | **单会话** + 记忆 / 知识库 / 梦境维护长内容 |
| 网关插件 | 独立 Python 仓库 | **不存在** |
