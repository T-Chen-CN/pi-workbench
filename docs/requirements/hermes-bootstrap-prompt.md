# Hermes 自举 Prompt：域名 / 反向代理 / 连接凭证

> 用途：用户把下方代码块里的整段内容粘给已经在服务器上运行的 Hermes Agent。
> 它会：判断现状 →（必要时）协助配好域名与反向代理 → 补齐连接凭证 → 验证 → 交付**一个文件**。
> 支持的形态：**域名 + 反向代理（HTTPS）**。不支持无域名 / 纯 IP 直连。
> 前提：执行者本来就能与 Hermes 对话（控制台登录或 SSH）。
> 状态：**草案，未验证**（还没有在干净机器上实跑过）。交付格式 **v1.1**（新增 `DASHBOARD_SESSION_TOKEN`，向后兼容 v1：缺这个字段只会让对话里的图片功能不可用）。已登记：[docs/README.md](../README.md) ·
> 待办与范围边界：[BACKLOG §7.3](../progress/BACKLOG.md)。

```text
# 任务：把云端 Hermes 配置到「可被 Pi Workbench 连接」的状态，并交付凭证文件

你是运行在这台服务器上的 Hermes Agent，拥有该机器的 shell 权限（可能通过 sudo）。
请按顺序执行下面六个步骤。不要长篇解释背景；每一步如实报告，做不到就明确说卡在哪一层并停止。

**支持的形态只有一种**：域名 + 反向代理 + HTTPS 证书。
如果这台机器无法达到这个形态（没有域名、或 80/443 无法放行），就按第一步的"阻塞"处理并停止，
不要用 IP 直连、自签证书或明文 HTTP 作为替代。

## 硬性禁止（违反即中止）

1. 不修改防火墙/网络策略：不改 iptables、nftables、ufw、firewalld、云安全组、任何自定义链。
   端口只做**检测并报告**，不放行、不封禁。
2. 不修改 DNS 记录。**除非**用户主动提供了 DNS 服务的 API 凭据，并且在你复述"将新增哪几条记录"后
   明确确认，才可以创建。否则只输出"需要用户手动添加的记录"，然后等用户完成。
3. 不轮换已有的 API 密钥。已存在就复用，只有缺失时才生成。轮换会让现有客户端全部失效。
4. **不停用、不卸载、不替换机器上已有的 Web 服务器**（nginx / apache / 已有的 caddy 实例）。
   只能在其上新增站点配置；若无法安全共存，报告并停止。
5. 不删除任何已有会话、配置、日志。修改任何文件前先备份：
   `cp -a <文件> <文件>.bak-$(date +%Y%m%d-%H%M)`
6. 不重启服务，除非本次确实改动了该服务的配置；重启前用一句话说明（会打断进行中的会话）。
7. **不得在对话里输出任何明文密钥**（API 密钥、控制台口令）。只允许脱敏形式，例如 `sk-****a1b2`，
   或"已写入交付文件"。这条没有例外。
8. 交付文件不得放在任何 git 仓库或 agent 工作区内，不得被 git 跟踪。

## 第一步：判断现状（只读，不改任何东西）

按顺序判断，命中即停，并把这个结论用作后面步骤的输入：

- **形态 A（齐备）**：已有反向代理，且 api / dashboard 两个域名的 HTTPS 都能从公网访问 → 跳到第三步。
- **形态 B（有域名，无反代）**：域名已解析到本机，但没有反向代理或没有证书 → 做第二、三步。
- **形态 C（没有域名 / 尚未解析）**：→ 执行下面的"域名准备"，再回到形态 B。

无论哪种形态，都先记录：

1. Hermes 版本。
2. 本机公网出口 IP（`curl -s https://ifconfig.me` 之类），后面告诉用户 DNS 要指向哪里。
3. 80 / 443 端口当前由谁占用（`ss -ltnp | grep -E ':(80|443)\b'`），以及已有的 Web 服务器。
4. 当前对公网提供 API 的是哪个 profile（结合 `~/.hermes/profiles/`、`systemctl list-units 'hermes*'`、
   反向代理配置里转发到的本地端口）。多个 profile 时选反代指向的那个，并说明判断依据。
5. API server 是否启用（profile 配置 / `.env` / 服务的 drop-in 或环境变量）。
6. 控制台的认证方式：反代层 basic auth（配置里有 `basic_auth` 一类指令）还是页面自带登录表单。
   用 `curl -s -o /dev/null -w '%{http_code}'` 配合页面内容判断，不要猜。
7. 现有 API 密钥位置（键名通常是 `API_SERVER_KEY` 一类）。找到就记下（不要打印全文），找不到标记为缺失。
8. 现有控制台口令：能读到或用户提供了就复用；读不到标记为"不可得"。

需要用户提供信息时，**把所有问题集中成一次提问**，不要反复打断。

## 第一步附：域名准备（仅形态 C）

1. 告诉用户需要**一个域名 + 两条 A 记录**，都指向本机公网 IP（上面查到的）：
   - `api.<域名>` → API 服务
   - `dash.<域名>` → 控制台
2. 给出可直接照抄的记录示例（类型 A、主机记录 api / dash、值 = 公网 IP）。
3. 检查 80 / 443 是否已放行。**未放行时不要尝试放行**，而是明确告诉用户：
   「证书申请需要 80 端口可达（HTTP-01），请你在云控制台的安全组里放行 80 和 443，我不会代做。」
   然后停止，等用户回来。
4. 等用户说"域名解析好了"之后，用 `dig +short api.<域名>` / `dash.<域名>` 验证是否已指向本机公网 IP。
   未生效就报告"还在传播中，未生效"并停止（不要继续配证书）。

## 第二步：反向代理与证书（形态 B / C）

1. 先看 80/443 的占用者：
   - 已有 nginx / apache → 在它上面**新增虚拟主机**，不要卸载、不要换端口。
   - 已有 caddy 在为别的站点服务 → 在现有 Caddyfile 里**追加站点**，不要覆盖整个文件。
   - 都没有 → 安装 Caddy（固定一个明确版本，校验下载来源），先备份 `/etc/caddy/Caddyfile`（若存在）。
2. 配置两个站点，要点：
   - `api.<域名>`：转发到 Hermes API 的本地端口；**必须关闭响应缓冲**以支持 SSE 流式输出
     （Caddy 用 `flush_interval -1`）。
   - `dash.<域名>`：转发到控制台的本地端口；给它较长的读超时（控制台页面/长连接）。
3. 应用配置前先做语法校验（`caddy validate --config ...` 或等价命令）。
4. 申请证书（HTTP-01）。**失败就报告失败**：不要退回自签证书，不要退回明文 HTTP。
5. 验证并记录：证书到期时间（`openssl s_client` + `x509 -noout -enddate`）、两个域名各自的 HTTP 状态码。

## 第三步：补齐凭证（只补缺口）

- API server 未启用 → 按该部署现有的方式启用（profile 配置或服务环境变量），备份后改，改动后重启该服务。
- API 密钥缺失 → 生成 32 字节随机串（如 `openssl rand -hex 32`），写入对应位置，权限 600。
- 控制台口令：
  - 已知 → 复用，**不改**。
  - 不可得 → 允许重置，但动手前必须先说：
    「接下来会重置控制台口令，现有已登录的控制台会话会被踢出，需要重新登录。」
    然后按该部署的认证方式重置（自带登录页按其 CLI/配置；反代 basic auth 则重新生成口令哈希并替换配置片段），
    原文件先备份。重置后不要回显口令，只写进交付文件。

## 第四步：验证（贴原始输出，不许只说"已确认"）

1. DNS：`dig +short api.<域名>` / `dash.<域名>` 指向本机公网 IP
2. 证书：`echo | openssl s_client -connect api.<域名>:443 -servername api.<域名> 2>/dev/null | openssl x509 -noout -enddate`
3. 鉴权：`curl -s -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $KEY" https://api.<域名>/v1/capabilities`
   期望 200（不要把真实密钥写进对话，用变量代入）
4. 控制台：`curl -s -o /dev/null -w '%{http_code}' https://dash.<域名>/`
   200 正常；被 basic auth 保护时未带凭据返回 401 也算正常，注明即可
5. 事件流链路：`curl -N -s --max-time 3 -H "Authorization: Bearer $KEY" https://api.<域名>/v1/runs/__probe__/events`
   只要不是连接失败/超时就算链路通（404、400 都可接受）
6. 端口：`ss -ltnp | grep -E ':(80|443)\b'`

不要为了验证去创建一个真实的 run（会产生 token 花费）。最多发只读请求。

## 第五步：交付（只给文件，不给明文）

写文件到 `~/.hermes/handoff/<profile>-<YYYYmmdd-HHMM>.txt`，权限 600，内容严格按下面格式：

# hermes-handoff v1.1
# 本文件含明文密钥，导入后请删除；需要重新生成时重跑本 Prompt。
PROFILE=
API_BASE_URL=
API_KEY=
DASHBOARD_URL=
DASHBOARD_USER=
DASHBOARD_PASSWORD=
DASHBOARD_SESSION_TOKEN=   # 控制台 /api/* 用的会话令牌（图片上传/回显）；没有就留空
AUTH_MODE=            # basic | form | none
HERMES_VERSION=
SERVER_HOST=
GENERATED_AT=
# ---- 校验结果 ----
dns_ok=
capabilities_http=
tls_not_after=
dashboard_http=
sse_ok=

写入后回读验证，并记录 `ls -l` 与 `sha256sum` 的输出。

格式版本是 **v1.1**：比 v1 只多 `DASHBOARD_SESSION_TOKEN` 一行。不知道令牌就留空（不要凭空编造），导入端会把 v1 与 v1.1 都认；缺令牌只是让对话里的图片功能不可用。

交付方式：

- 通道支持发送文件/附件：直接把该文件发给用户。
- 通道不支持：在对话里给出用户在自己电脑上执行的命令（占位符保留，不要带密钥），例如
  `scp -i <你的私钥> ubuntu@<服务器地址>:~/.hermes/handoff/<文件名> .`
- 两种情况都要在对话里给出：文件路径、`ls -l`、`sha256sum`、脱敏预览
  （例如 `API_KEY=sk-****a1b2`、`DASHBOARD_USER=<用户名>`、`AUTH_MODE=<basic|form>`）。
- **绝对不要**在对话里出现 `API_KEY=` 或 `DASHBOARD_PASSWORD=` 的真实值。

## 第六步：收尾报告（简短）

1. 一句话结论：可用 / 有阻塞。
2. 本次属于哪种形态（A / B / C），做了哪些改动，备份在哪。
3. 过程中提出的所有问题（没有就说"无"）。
4. 任何一项验证失败时，说明卡在哪一层（DNS / 证书 / 反代 / 服务 / 鉴权 / 控制台），不要凭猜测给结论。
5. 给用户三行操作提示：
   - 把文件导入 Pi Workbench 的「连接」页（支持从文件导入），或按文件内容填地址与密钥
   - 导入后请删除该文件
   - 需要作废时重跑本 Prompt 并说明「请轮换 API 密钥」（轮换会踢掉现有客户端）

## 边界

- 本次任务会读取服务器上的密钥文件，这是用户明确要求的。
- 如果用户说"只是自己用、别重置控制台口令"，以用户的要求为准。
- 只能用域名 + 反向代理 + HTTPS 这一种形态；不提供 IP 直连、自签证书、明文 HTTP 的替代方案。
- 任何一步失败都不要往下猜，报告并停止。
```
