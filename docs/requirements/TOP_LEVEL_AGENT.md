## 1. 背景与目标

### 1.1 现状（读代码得来，不是设想）

- `electron/agent-registry.ts`：**一工作区一 `AgentManager`**，键是 `workspaceDir`；`agent:initialize` 以工作区为单位初始化。
- `pi-bridge/src/agent-manager.ts`：`agentDir` 固定为 `{appDir}/data/agent`（全局），`sessionDir = {appDir}/data/agent/sessions`（全局），但**会话按 cwd 归属**——`SessionManager.list(workspaceDir, sessionDir)` 只列出 cwd 等于该工作区的会话；工具根、上下文资源发现都以会话 cwd 为原点。
- 本应用已有「会话 root 可偏离实例 workspaceDir」的先例：`resolveSessionRoot` / `requestSessionRoot` / `worktree-extension` 让会话在轮次边界切到另一个目录。
- 权限：`pi-bridge/src/approval-policy.ts` 的矩阵 + `electron/approval-broker.ts`；**会话是权限的唯一权威**，`readonly` 对写/命令/其它一律 `deny`，审批 120s 超时即 deny（fail-closed）。
- 信任：`electron/workspace-trust.ts` + `main.ts` 的 `seedTrustedWorkspaces()`——启动时把 `workspaces.db` 里**所有已收录工作区**登记为受信任根，**与是否打开无关**。
- 界面：每个打开的工作区挂一份常驻 `WorkspaceView`（`visibility: hidden` + `inert` 切换）；会话标签落盘在 `{workspace}/.pi-workbench/chat-tabs.json`，由该工作区的渲染层状态维护。
- 首页：`WelcomeScreen.tsx` 目前是「欢迎 + 最近工作区」，没有常驻会话。

### 1.2 目标

- 首页有一个**顶层会话**，用户对它说「把 A 项目的登录模块重构掉」，它自己决定去 A 工作区派发任务、跟进、汇报，用户不需要先切工作区、再重复一遍需求。
- 顶层可以推进**所有已收录工作区**，包括当前没打开的工作区。
- 顶层可以请求**新增工作区**，但必须由用户确认。
- 推进过程对用户可观察、可干预、可撤销授权、可事后审计。

### 1.3 本轮讨论确立的结论

1. **A1 编排型**：顶层不做文件级执行。它拆解、派发、跟进、汇总；真正读写由**目标工作区里的子会话**完成。
2. **B 范围**：已收录工作区（`workspaces.db`）+ 新增工作区能力（两条入口都要，见 Q2）。
3. **C 驻留**：顶层会话暂时住在**首页**（[确认·暂定]，信息架构见 4.7）。
4. **D 委派授权**：在顶层获批一次，即可接管其下所有工作区的授权（细则见 4.5，这是本需求唯一的**安全边界变更**）。
5. **E 不依赖打开**：委派与任务推进不要求目标工作区处于打开状态，`WorkspaceView` 是否存在不影响执行。

### 1.4 状态标记

- `[确认]`：本轮讨论中用户明确确认。
- `[推断]`：由确认项推导出的必要行为，仍需用户点头（相应条目在 §7 列出）。
- `[待确认]`：尚未决定，实现前必须收敛。

## 2. 术语

| 术语 | 定义 |
| --- | --- |
| 顶层会话 | 不隶属于任何工作区的常驻会话，驻留首页，负责拆解与派发。它有独立 cwd（虚拟 scope），不在任何工作区列表里出现。 |
| 子会话 | 顶层在某个工作区里创建（或复用）的真实会话。cwd = 该工作区根，历史 / 导出 / 分支 / 压缩等既有机制全部照旧。 |
| 已收录工作区 | 记录在 `data/workspaces.db` 的工作区。启动即受信任（现状）。 |
| headless 工作区 | 已收录但当前**没有**打开标签（无 `WorkspaceView`、无文件监听）的工作区。 |
| 派发 | 顶层把一段任务说明交给某工作区的子会话执行并开始等待结果。 |
| 任务 | 一次派发产生的第一类对象：有 id、目标工作区、说明、状态、子会话、授权、时间线。 |
| 委派授权 | 顶层被用户批准后，为其名下的子会话签发的写/命令/其它类别授权。不写进子会话自身的持久权限。 |
| 接管 | 用户直接在目标工作区里打开子会话并发言，优先级高于顶层的下一次派发。 |
| 阻塞 | 任务需要人做决定（审批被拒、缺凭证、冲突需裁决）而暂停，等待用户在任务视图处理。 |
| 轮次边界 | 一次 Agent 运行结束、没有在途工具调用的时刻（SDK `agent_settled`），沿用工作树会话的既有定义。 |

## 3. 核心模型

### 3.1 三层身份变成四层

现状是「应用 → 工作区 → 会话」。「顶层会话」不隶属于任何工作区，所以引入**与工作区并列的一层**：

```
应用
├── 顶层（虚拟 scope，cwd = {appDir}/data/agent/orchestrator）
│   └── 顶层会话（可多个，但默认一个）
└── 工作区（N 个，含 headless）
    └── 会话（含顶层派发的子会话）
```

要点：

- 顶层会话**不是**「一个特殊工作区」：它没有 `.pi-workbench/`、没有文件树、没有 Git 视图、没有终端、没有编辑器标签。它只有一个会话记录和一套编排工具。
- 顶层会话的 cwd 是虚拟目录，**不参与**任何文件操作（见 4.1 与 4.4）。这个目录只用于让 SDK 与既有会话机制正常工作。
- 会话记录的真相源不变：仍是 `{appDir}/data/agent/sessions/*.jsonl`，仍按 `parentId` 分支重建时间线。顶层会话与子会话的记录都在这里，只是 cwd 不同。

### 3.2 控制面与执行面

| | 控制面（顶层） | 执行面（子会话） |
| --- | --- | --- |
| 位置 | 首页 | 目标工作区（headless 时无界面） |
| cwd | 虚拟 scope | 工作区根（或该会话绑定的工作树） |
| 能读文件 | 是，跨已收录工作区只读（4.4） | 是 |
| 能写文件 / 跑命令 | **否** | 是（需有效权限或委派） |
| 产出 | 任务、汇报、对用户的追问 | 文件改动、命令输出、工具轨迹 |

### 3.3 权限来源图（本需求唯一的边界变更）

现状：`用户 →（审批）→ 会话`。
新增：`用户 →（审批一次）→ 顶层会话 →（委派）→ 子会话`。

**约束**：委派只能**下放顶层自己拥有的能力**，不能放大。顶层没有 write 能力时，不可能给子会话签发 write 授权。

### 3.4 任务是一等对象

任务不是「某条聊天消息的附属品」，而是有独立生命周期、独立持久化、可被顶层与用户同时观察的对象。它引用：`taskId` / `workspaceRoot` / `sessionId` / `delegationId` / 状态 / 时间线。状态机见 4.6。

## 4. 功能需求

### 4.1 顶层会话（身份、驻留、模式）

- **TL-A01** `[确认]` 顶层会话驻留首页，不在任何工作区的会话列表与标签里出现。
- **TL-A02** `[推断]` 顶层会话的 cwd 固定为 `{appDir}/data/agent/orchestrator`（启动时创建空目录）。不因此目录被列入受信任工作区，也不因此获得文件工具。
- **TL-A03** `[推断]` 默认只有一个顶层会话；同名「新建顶层会话」能力暂不提供（可后续按普通会话语义扩展）。
- **TL-A04** `[推断]` 顶层会话沿用现有会话机制中与工作区无关的部分：JSONL 记录、分支、压缩、导出、标题生成、思考展示。不沿用：工作区标签恢复、文件改动卡、Git 视图联动。
- **TL-A05** `[推断]` 顶层会话的模式（`readonly` / `plan` / `ask` / `auto`）沿用现有 `SessionMode`，默认从全局默认档生成，随会话落盘。它是**委派的上限**（见 4.5.4）。
- **TL-A06** `[推断]` 顶层会话与子会话共用全局模型配置（`data/agent/models.json`），不新增「顶层专用模型」；如需分层，见 §10 P4。
- **TL-A07** 顶层会话的上下文里**不注入任何工作区的环境段落**（工作目录、规矩、工作树状态）；它需要的最新事实通过工具查询（4.3）。避免「你以为的 A 项目」与「真实的 A 项目」漂移。

### 4.2 工作区清单与新增工作区

- **TL-B01** `[确认]` 顶层可枚举**全部已收录工作区**（`workspaces.db`），包括未打开的。清单项至少包含：路径、名称、是否已打开、最近活动时间、当前任务数、Git 分支（能取到就取，取不到留空）。
- **TL-B02** `[确认]` 顶层可推进未打开的工作区；打开与否不影响执行（对应 §4.8）。
- **TL-B03** `[确认]` 顶层可**请求**新增工作区。
- **TL-B04** `[推断]` 新增工作区的两条入口都落回主进程批准，渲染层仍不得自行注册任意目录：
  - (a) 用户在首页点「添加工作区」→ 原生选择器 → `trustWorkspace()` + 写入 `workspaces.db`。
  - (b) 顶层调用 `add_workspace` 工具传路径 → 首页弹出确认卡（显示 `canonicalizePath` 规范化后的真实路径与是否存在）→ 用户确认后才 `trustWorkspace()` + 写入 `workspaces.db`。
- **TL-B05** `[推断]` 新增只「收录」，**不自动打开标签**（与 E 一致）；首页任务看板显示为未打开。用户可随时手动打开。
- **TL-B06** `[待确认]` 目标路径不存在、越权（如 `C:\Windows`）、或是受保护目录时，请求必须被拒绝并回给顶层明确错误，不做任何创建。

### 4.3 派发与子会话

- **TL-C01** `[确认]` 派发在目标工作区**创建新子会话**（不复用用户正在用的会话），原因：避免两条输入流写同一个会话、避免污染用户自己的上下文与权限档。
- **TL-C02** `[推断]` 子会话的 cwd = 目标工作区根；`.pi-workbench/` 不存在时**懒创建**（与 `workspace:init` 同样的目录结构），不改变 `workspaces.db` 的 `open_count`。
- **TL-C03** `[推断]` 子会话必须能在目标工作区里被用户找到：打开该工作区时，子会话出现在会话列表，标注「由顶层派发」与所属任务；未打开时只出现在首页任务看板（`chat-tabs.json` 由该工作区的渲染层维护，headless 时无人写入，因此**不会**自动进入打开标签）。
- **TL-C04** `[推断]` 一次派发携带：任务说明、期望产出（代码改动 / 结论 / 调研）、是否允许写、目标工作区、可选的基线与约束（如「只在这两个目录里改」）。说明由顶层撰写，用户可见。
- **TL-C05** `[推断]` 顶层通过工具读取子会话进展：状态、最近一轮的回复摘要、工具轨迹摘要、文件改动清单、失败原因。默认不把子会话完整上下文塞进顶层上下文；需要细节时按需拉取（按 `toolCallId` / 消息 id 取片段）。
- **TL-C06** `[推断]` 顶层可以：等待、继续追问、追加说明（`steer`）、停止任务、取消任务。停止与取消的语义区别见 4.9。
- **TL-C07** `[待确认]` 子会话间**不通信**；所有跨工作区的信息交换都必须经顶层（避免网状依赖与不可追踪的写入）。
- **TL-C08** `[推断]` 派发不绕过审批：子会话的每次写/命令调用，要么被有效委派覆盖，要么照旧弹审批卡（见 4.5）。

### 4.4 顶层可用的工具集

- **TL-D01** `[推断]` 顶层工具集分两组，**不含** `write` / `edit` / `bash` / `powershell` / `submit_plan`：

| 组 | 工具 | 说明 |
| --- | --- | --- |
| 观察 | `list_workspaces` / `workspace_status` | 工作区清单与单工作区概况（分支、脏文件数、最近提交） |
| 只读 | `read` / `grep` / `find` / `ls` | **仅限已收录工作区**，多根解析；越界路径返回明确错误 |
| 编排 | `dispatch_task` / `task_status` / `task_report` / `steer_task` / `stop_task` / `list_tasks` | 派发与跟进 |
| 工作区 | `add_workspace` | 请求新增（需用户确认） |

- **TL-D02** `[推断]` 顶层只读工具与既有 `read` 类的权限语义一致：在 `readonly` / `plan` 模式也可用，且永不触发审批。
- **TL-D03** `[推断]` 顶层只读的范围是**运行时快照**（已收录工作区集合），新增 / 移除工作区时刷新；顶层不得缓存「上一次看到的文件内容」当作事实，涉及改动的结论必须来自子会话的最新汇报。
- **TL-D04** `[待确认]` 顶层是否需要 `web_search` 等联网工具（用于调研类任务）。倾向：给，且与只读类同权限。

### 4.5 委派授权（安全边界，逐条实现）

#### 4.5.1 授权对象

```
DelegationGrant {
  id, taskId,
  topSessionId,
  workspaceRoot,            // 单个工作区
  categories: ('write'|'command'|'other')[],
  issuedAt, revokedAt?,
  approvedBy: 'user',        // 只能来自用户显式批准
}
```

- **TL-E01** `[确认]` 授予粒度：**按 类别 × 工作区**，不是「一次给全部」。写、命令、其它三类分开。
- **TL-E02** `[推断]` `read` 类永远不受委派影响（现状矩阵已是 allow）。
- **TL-E03** `[推断]` 授权**跟随任务**：任务进入终态（完成 / 失败 / 取消）即失效。
- **TL-E04** `[推断]` 授权**不写进**子会话的 `data/agent/session-extras/<id>.json` 的 `permission` 字段。子会话手动打开时的权限仍从它自己的档案（或全局默认档）生成。这是硬要求：防止一次委派变成该会话的永久授权。

#### 4.5.2 触发与展示

- **TL-E05** `[确认]` 一次交互完成全部签发：用户批准一次，即为该任务涉及的每个工作区各签发一份 grant（不需要每个工作区各批一次）。
- **TL-E05b** `[推断]` “一次交互”不等于“一份无边界授权”：哪份 grant 失效（如某个工作区被撤销）只影响那个工作区。
- **TL-E06** `[推断]` 批准发生在**首次派发需要写能力时**，首页弹委派卡，内容必须包含：目标任务、涉及的每个工作区路径、获得的类别（写 / 命令）、失效条件（任务结束）。
- **TL-E07** `[推断]` 委派卡与现有 `ApprovalCard` 使用同一套交互与超时语义：120s 无响应即视为拒绝，任务进入阻塞，不静默放行。
- **TL-E08** `[推断]` 若一个任务只做只读调研，不弹委派卡、不签发任何授权。

#### 4.5.3 判定顺序（子会话的工具调用）

1. 会话自身 permission 为 `readonly` 或 `plan` → `deny`（**用户显式设定优先于委派**，不下放）。
2. 存在**有效且覆盖该类别**的委派授权 → `allow`，并记录 `authorizedBy: delegationId`。
3. 否则按会话自身矩阵：`ask` 弹审批卡 / `auto` 放行 / `readonly` deny。

- **TL-E09** `[推断]` 第 1 条的含义：用户手动把子会话设成只读，委派对它无效。这是用户手里最强的一票，优先于顶层。
- **TL-E10** `[待确认]` 子会话权限为 `null`（未固化）时按全局默认档判定，而默认档可能是 `readonly`；此时委派是否生效？倾向：**生效**（委派优先于「未固化的默认档」，但不优先于「用户显式设定」）。

#### 4.5.4 上限与放大禁止

- **TL-E11** `[推断]` 可签发类别 ⊆ 顶层会话模式允许的类别。顶层 `readonly` / `plan` 时**不能**签发任何写/命令委派；界面上不允许发起此类任务（提示先切模式）。
- **TL-E12** `[推断]` 委派不能跨应用重启存续；重启后一律回到待确认（见 4.10）。

#### 4.5.5 撤销与审计

- **TL-E13** `[推断]` 用户可在首页任务视图随时撤销单个任务的委派；撤销后**后续**写/命令调用一律 `deny`（在途调用不打断），子会话收到拒绝理由并被要求汇报阻塞点。
- **TL-E14** `[推断]` 每次因委派而放行的写/命令调用都必须可审计：`logs/agent.log` 记录 `taskId` / `delegationId` / `workspaceRoot` / 工具名 / 时间；任务时间线里可见。
- **TL-E15** `[推断]` 首页任务视图显示当前生效的委派（工作区 + 类别），并在任务结束后自动消失。

### 4.6 任务状态机与并发

状态：`queued` → `running` → `blocked` / `done` / `failed`；另有 `cancelled`、`paused`（重启后）。

| 状态 | 含义 | 谁能离开它 |
| --- | --- | --- |
| `queued` | 已派发，等目标工作区空闲（同工作区单写者） | 队列轮到自己 → `running`；用户取消 → `cancelled` |
| `running` | 子会话正在跑 | 子会话结束 → `done` / `failed`；需要人决策 → `blocked` |
| `blocked` | 需用户决定（委派被拒、缺凭证、冲突裁决、审批超时） | 用户在任务视图处理 → `running`；放弃 → `cancelled` |
| `done` / `failed` | 终态，附汇报 | — |
| `paused` | 应用重启前未完成 | 用户点「继续」→ `queued` |
| `cancelled` | 用户中止 | — |

- **TL-F01** `[推断]` **同工作区单写者串行**：同一工作区同一时刻只有一个处于 `running` 的任务；其余排队。跨工作区可并行。理由：文件冲突与 Git 竞态没有便宜解法，工作树会话只能解决不同分支的并行，不能解决同目录并发。
- **TL-F02** `[推断]` 全局并行上限默认 3 个 `running` 任务（配置项，可后续开放）；超出的排队。
- **TL-F03** `[推断]` 只读任务（不需要委派的任务）不受单写者约束，可以与写任务并行；但不得与同一工作区的写任务同时段执行命令（避免“读到的文件是我改到一半”）。
- **TL-F04** `[待确认]` 用户在目标工作区里正人工使用会话时，是否仍允许派发写任务到该工作区？倾向：允许，但在委派卡上明示“该工作区有人正在操作”，单写者串行只约束顶层任务，不约束人工操作。
- **TL-F05** `[推断]` 一个任务只对应一个子会话；需要拆得更细时，由顶层派发多个任务（各自排队），不在单个会话里并行。

### 4.7 与用户的交互（首页信息架构 [确认·暂定]）

首页自上而下：

1. **顶层对话区**：常驻会话，包含流式输出、过程轨迹、工具调用、审批 / 委派卡。
2. **任务看板**：按状态分组（运行 / 排队 / 阻塞 / 最近完成），每张卡显示：目标工作区、一句话目标、状态、耗时、生效委派、可操作项（查看 / 继续 / 停止 / 取消 / 撤销授权 / 打开工作区 / 跳到子会话）。
3. **最近工作区**：沿用现有列表，增加“任务进行中”标记。

- **TL-G01** `[推断]` 工作区视图内必须有顶层入口：状态栏指示（“顶层：N 个任务运行中 / 1 个待处理”）+ 点击回首页；阻塞与完成事件走现有 `notifications.ts` 路由，提示可跳回首页。
- **TL-G02** `[推断]` 阻塞必须有单一入口集中处理：首页任务看板里的阻塞区列出所有需要用户决定的项，并说明“需要什么”。
- **TL-G03** `[推断]` 从任务卡可“打开工作区并定位到子会话”（打开标签 + 恢复会话）；反向亦然（子会话里显示“属于任务 X”）。
- **TL-G04** `[待确认]` 顶层面板是否允许拆出成独立窗口（复用 `aux:*` 机制）。倾向：允许，与现有面板一致；但首版可不做。
- **TL-G05** `[推断]` 顶层会话的权限/模式切换入口与普通会话一致（现有聊天头部控件）；子会话的模式由用户手动改时，委派立即失效（见 TL-E09）。

### 4.8 Headless 工作区

- **TL-H01** `[推断]` 未打开的工作区**可以**接任务：不创建 `WorkspaceView`、不开文件监听、不写 `chat-tabs.json`。
- **TL-H02** `[推断]` headless 工作区的 `AgentManager` 生命周期：任务运行时保留；任务结束后**空闲 10 分钟释放**（会话 JSONL 保留，下次派发重建）。这是对现有铁律“关闭标签是唯一回收入口”的必要补充，需在 [paths-and-storage](../agent/paths-and-storage.md) 登记为第二个回收入口。
- **TL-H03** `[推断]` 不在 headless 工作区创建终端、不做 Git 视图刷新、不弹文件改动卡；这些能力在用户打开该工作区后自然可用。
- **TL-H04** `[推断]` 用户随时可对一个正在跑任务的 headless 工作区“打开”；打开后不重启会话、不断流（沿用现有“已有会话接入”语义）。
- **TL-H05** `[推断]` 关闭工作区标签时：若该工作区有 `running` / `queued` 任务，走现有“忙碌确认”弹窗，选项包含“仅关闭界面，任务转入后台继续”——即关闭后回到 headless 状态而不是杀掉任务。

### 4.9 停止、失败与成本

- **TL-I01** `[推断]` `stop_task`（顶层主动）= 中止当前轮次 + 任务进入 `queued` 待重新派发；`cancel`（用户）= 中止并进入 `cancelled`。两者在 UI 上必须分开。
- **TL-I02** `[推断]` 失败分类必须落到任务卡：供应商报错 / 工具失败 / 用户拒绝授权 / 审批超时 / 子会话崩溃。可重试的给“重试”按钮，不可重试的说明原因。
- **TL-I03** `[推断]` 顶层不得自行无限重试：同一任务连续失败 2 次后强制进 `blocked`，交用户决定。
- **TL-I04** `[待确认]` 成本汇总：任务卡是否聚合顶层 + 子会话的 token 用量。倾向：聚合，只显示数字，不引入预算控制。

### 4.10 持久化与恢复

| 内容 | 位置 | 语义 |
| --- | --- | --- |
| 顶层会话记录 | `{appDir}/data/agent/sessions/*.jsonl`（cwd = 虚拟 scope） | 现状机制，真相源不变 |
| 子会话记录 | 同上（cwd = 目标工作区） | 与普通会话完全一致 |
| 任务与委派 | `{appDir}/data/agent/orchestrations/<taskId>.json` | 原子写（`atomic-json`）；包含状态、时间线摘要、委派历史、子会话 id |
| 顶层会话 mode | `data/agent/session-extras/<id>.json` | 现状机制 |

- **TL-J01** `[推断]` 任务落盘必须是**增量追加式**的时间线摘要，不是完整对话副本（完整内容去 JSONL 拿）。单文件大小设上限（建议 256 KB），超过只保留最近 N 条 + 首尾摘要。
- **TL-J02** `[推断]` 重启后：任务恢复为 `paused`，首页展示“上次运行时未完成”分组，用户点“继续”才重新派发。**不自动续跑**（无人监督的写操作）。
- **TL-J03** `[待确认]` 是否允许“只读类任务自动续跑”（不碰文件、不跑命令）。倾向：允许，需在设置里有一开关。
- **TL-J04** `[推断]` 委派永不跨重启（TL-E12）：恢复时必须重新批准，即历史委派记录只作审计，不再生效。
- **TL-J05** `[推断]` 任务记录在用户“删除 / 归档”后清理（与普通会话生命周期一致），不另设清理策略。

## 5. 验收场景

| 编号 | 场景 | 期望 |
| --- | --- | --- |
| TL-01 | 首页对顶层说“看看 A 项目的测试怎么跑的” | 只读任务投递到 A，不弹委派；汇报回到首页，任务卡可跳子会话 |
| TL-02 | 派发到**从未打开**的工作区 | 自动懒创建 `.pi-workbench/`；无 `WorkspaceView` 也能跑完；任务卡标“未打开” |
| TL-03 | 同一工作区连派两个写任务 | 第二个排队（`queued`），第一个完成后自动开始；不会两个同时改文件 |
| TL-04 | 同时向 A、B 两个工作区派写任务 | 首次弹一张委派卡，列出 A、B；批准后两边并行，各自子会话不再逐次弹写审批 |
| TL-05 | 撤销任务 X 的委派 | 子会话下一次写调用被 deny，任务进 `blocked`，阻塞区给出原因与继续选项 |
| TL-06 | 任务结束后手动打开该子会话并发“改个文件” | 重新要求审批（委派不泄漏成持久授权） |
| TL-07 | 顶层处于 `readonly` / `plan`，请求写任务 | 直接拒绝并说明原因；不会出现任何写委派；子会话不获得写能力 |
| TL-08 | 用户把子会话手动设为 `readonly` | 即使任务带有写委派，子会话写操作仍被 deny |
| TL-09 | 任务运行中用户在目标工作区打开子会话发言 | 发言以 `steer` 送达；顶层下一次派发需等待轮次边界，不出现双写 |
| TL-10 | 新增工作区两条入口 | (a) 选择器选择即收录且受信任；(b) 顶层请求弹确认卡，拒绝后不收录不创建 |
| TL-11 | 任务中途关闭应用重启 | 任务显示为 `paused`；不自动续跑；点继续后重新批准委派才继续 |
| TL-12 | 关闭正在运行任务的工作区标签 | 提示“仅关闭界面、任务转后台”；关闭后任务继续，重现打开时能接上子会话 |
| TL-13 | 审计 | 在 `logs/agent.log` 能用 `taskId` 串起每一次因委派放行的写/命令调用 |
| TL-14 | 顶层把路径走到工作区外 | 只读工具返回明确越界错误；不会静默失败或构造伪内容 |
| TL-15 | 子会话因审批超时 / 供应商报错卡住 | 任务进 `blocked`，失败分类正确，不无限重试 |

## 9. 非目标

- 顶层直接改文件 / 跑命令（属于 A2 特权型，已否决）。
- 子会话之间直接通信或互相等待（网状依赖不可追踪）。
- 跨工作区的原子提交、统一 Git 历史、多仓事务。
- 无人监督的自动重试、自动续跑、自动接受风险操作。
- 跨机器 / 云端任务队列。
- 给顶层单独的模型配置与预算控制。
- 顶层自带终端、文件树、Git 视图、编辑器。
