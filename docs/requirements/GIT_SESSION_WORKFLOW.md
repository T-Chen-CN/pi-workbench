# Pi Workbench Git 会话工作流需求文档

**状态**：Draft v1.7（需求已对齐，待设计评审）  
**日期**：2026-10-26  
**范围**：多会话单工作区下的 Git 分支、工作树、提交、合并、推送与 Git 视图  
**不包含**：技术实现、第三方库选型、视觉稿

---

## 1. 背景与目标

Pi Workbench 当前支持一个工作区内多个聊天会话并行运行。用户希望每个会话都有独立的 Git 分支上下文，能够并发修改、查看分支与提交、按需提交/合并/推送，并且有一个类似 VS Code GitLens 的只读 Git 视图；同时，一个会话可以同时持有多个仓库的工作树。

本文件记录已确认的需求基线。

**状态标记**：

- `[确认]`：来自用户明确回答。
- `[推断]`：由回答直接推导出的必要行为，仍需用户点头。
- `[待确认]`：尚未决定。

---

## 2. 术语

| 术语 | 定义 |
| --- | --- |
| 逻辑工作区 | 用户打开的项目目录；会话、设置、Git 视图的逻辑容器；可以包含多个 Git 仓库 |
| 会话 | 一个聊天对话线程；同一时间只处理一个任务、一个提交；每个参与的仓库各有一个当前工作树和当前分支 |
| 工作树 | Git worktree；每个写会话在每个参与的仓库中拥有一个独立工作树和独立 HEAD |
| 会话分支 | 会话当前写入的分支；首次写操作时创建；按仓库独立 |
| 基分支 | 创建会话分支时所基于的分支；默认是该仓库加入会话时的当前分支 |
| 目标分支 | 合并/推送时指定的分支；默认基分支，用户可指定 |
| stash | Git 标准机制：把工作树和暂存区的未提交改动保存成一条 stash 记录，工作树恢复干净；之后可以 apply/pop 回来。它不是分支也不是提交，存在于仓库的 stash 列表；跨工作树 apply 可能冲突。应用内的 stash 记录带会话/分支/时间标签，便于在 Git 视图找到。 |
| detached HEAD | HEAD 直接指向某个提交而不是分支。此状态下的新提交不属于任何分支，除非先创建分支。 |
| 子模块（submodule） | 嵌套在父仓库中的另一个 Git 仓库；父仓库只记录子模块的提交指针，子模块内的改动属于子模块仓库。 |
| LFS | Git Large File Storage；大文件由 git-lfs 管理，需要本机安装 git-lfs；diff/恢复可能只看到指针文件。 |
| 多仓库工作区 | 一个逻辑工作区里包含多个 Git 仓库；会话可以同时持有多个仓库的工作树。 |

---

## 3. 核心模型

- 一个会话同一时间只处理一个活动仓库、一个当前分支、一个提交；不再用“任务”作为边界。
- 会话可以在一个或多个仓库中工作；每个参与的仓库各有一个当前工作树和一个当前分支；**可以同时持有多个仓库的工作树，但同一时间只有一个活动仓库/分支**（Q9）。
- 一个会话可以在多个仓库分别提交；同一时间只处理一个提交；**跨仓库不能原子提交**。
- **允许顺序产生多个提交**：一个提交完成后，可以在同一会话内继续下一个提交（Q1）。
- 写会话在第一次写操作时为当前仓库创建分支和工作树；只读会话不创建。
- 一个分支同一时间只能被一个工作树写入（按仓库判断）。
- 读操作不受限制：任何会话都可以读取其他分支、提交和 diff。

> 注：Q1 的“一个分支”按“每个参与仓库各一个当前写分支”理解；多仓库会话可以同时持有多个仓库的当前分支，但同一时间只处理一个提交。

## 4. 功能需求

### 4.1 并发与工作树

**GIT-001 `[确认]` 并发会话与写隔离**  
同一逻辑工作区下允许多个会话并发运行。写会话之间文件级隔离；同一个文件可以被不同会话在不同工作树中同时修改。

**GIT-002 `[确认]` 每写会话独立工作树**  
每个写会话在每个参与的仓库中拥有独立的 Git 工作树和独立分支。只读会话不创建工作树/分支，可共享读取。

**GIT-003 `[确认]` 统一的工作区文件视图**  
工作区文件视图显示逻辑工作区下所有参与仓库的文件，至少包括：

- 每个仓库当前工作树的文件；
- 工作树之外的文件（例如工作区根目录下的共享文件、应用配置、未纳入任何工作树的文件）。

默认显示“当前仓库/工作树 + 工作树外文件”；可以按仓库/工作树切换查看。同一路径存在于多个工作树时，默认显示当前工作树的版本，并标明其他工作树是否有差异。

**GIT-004 `[确认]` 用户与 Agent 同工作树编辑**  
用户可以在当前会话对应的工作树内直接编辑文件，与 Agent 的修改同时生效，不互相阻塞。若用户有未保存的编辑、Agent 又修改了同一文件，必须检测并提示（重新加载 / 保留我的 / 查看差异），不能静默覆盖。

**GIT-005 `[确认]` 会话间读可见**  
多个会话之间可以以只读方式看到彼此的改动，至少包括：文件状态、diff、变更列表，无需手动刷新。  
这不是实时协作编辑：写入仍然隔离，冲突在合并时处理（Q2）。

**GIT-006 `[确认]` 只读会话共享**  
只读会话可以读取所有仓库的工作树/分支的内容，但不能写文件或执行 Git 写操作。

### 4.2 分支与会话生命周期

**GIT-010 `[确认]` 分支懒创建与脏工作区处理**  
会话启动时不创建分支。只有出现第一次写操作时，才为当前仓库创建分支和工作树。只读会话不创建分支。  
如果首次创建会话工作树时当前工作树是主工作树且存在未提交改动，默认将这些改动 **stash 后 apply 到新工作树**，主工作树恢复干净（Q7/Q8 选 c）；apply 成功后 drop 这个临时 stash。  
如果当前工作树是已有 linked worktree（只读），不移动它的未提交改动；会话从该工作树的 HEAD 创建新分支和工作树。  
如果当前工作树属于另一个会话，不能自动移动，改为询问用户。

**GIT-011 `[确认]` 每会话一个当前写分支**  
每个会话同一时间只有一个活动仓库和一个当前写分支。允许切换，但切换后仍然只管理一个分支。  
跨仓库可以各有一个当前分支，但同一时间只有一个活动仓库/分支；不得在同一仓库内为一个会话同时维护多个写分支。

**GIT-012 `[确认]` 分支不能跨会话共用**  
按仓库判断：不同会话不能同时使用同一个分支。同一分支同一时间只能被一个工作树检出。  
如果用户要求两个会话共用一个分支，系统必须要求改为：新建分支、合并为一个会话，或串行使用。

**GIT-013 `[确认]` 写范围与读范围**  
会话只能写自己在各仓库的当前分支；可以读取其他分支、提交、diff；可以合并/推送到用户指定的目标分支（包括基分支）。  
会话可以同时持有多个仓库的工作树；每个仓库有独立的当前分支和工作树。

**GIT-014 `[确认]` 切换分支的脏改动处理**  
切换分支时如果存在未提交改动，Agent 必须在对话中主动询问用户（Q3）。用户可以选择：提交、stash、放弃改动、取消切换。  
不使用审核弹窗。切换只影响当前仓库的分支，不影响其他仓库。  
选择 stash 后，切回该分支不会自动 apply；stash 保留在列表，按 GIT-079 处理。

**GIT-015 `[确认]` 会话结束时的分支与工作树**  
会话结束包括：关闭会话标签、删除会话、关闭工作区标签、退出应用；崩溃按异常处理。

会话结束时：

- 保留分支和提交；
- 如果本会话创建的工作树有未提交改动，**自动 stash 保留**（stash 记录带会话/仓库/分支/时间标签，Q4）；
- 删除本会话创建的工作树；
- 已有工作树不自动 stash、不删除，用户改动保持原样；
- 分支可以被其他会话接管（其他会话可为该分支新建工作树）；
- 不自动清理分支。

如果 stash 失败，不得删除工作树；报告失败并等待用户处理。  
**工作树只在会话结束时删除；会话运行期间不删除。**  
崩溃/异常退出无法执行 stash，按异常清理处理，未提交改动可能丢失；已生成的 stash/commit 保留。

如果本会话创建的工作树存在未完成的 merge/rebase（包括 cherry-pick/revert 中断状态）：

- 默认阻止关闭/退出；
- 使用现有会话关闭确认，提示“有未完成的合并/变基，关闭会丢失进度”，提供“中止操作并关闭”和“取消”；
- 选择中止：先 abort，再 stash 已跟踪+未跟踪改动，最后删除工作树；
- 选择取消：保持会话和工作树不变；
- 不使用独立的 Git 审核弹窗，也不保留工作树作为例外。

**GIT-016 `[确认]` 合并目标**  
合并目标默认是该仓库加入会话时的基分支；如果用户在会话中指定了目标分支，则合并到指定分支。  
多仓库时，合并目标按仓库分别确定。

**GIT-017 `[确认]` 不自动清理**  
应用不自动删除分支，不自动丢弃未提交改动。  
自动执行的只有：按 GIT-015 自动 stash 未提交改动、删除本会话创建的工作树。  
合并完成后不触发清理；其余清理由用户显式操作（Q6）。

**GIT-018 `[确认]` 多仓库并行**  
支持一个逻辑工作区包含多个 Git 仓库，并且一个会话可以**同时持有多个仓库的工作树**（Q9）。  
要求：

- 每个参与仓库有独立的当前分支、工作树和提交历史；
- 仓库选择器可以提前把某个仓库设为当前活动仓库；同一时间只有一个活动仓库/分支；首次写某个仓库时才创建该仓库的会话工作树和分支；
- 文件视图和 Git 视图可以按仓库切换/过滤，看到所有参与仓库；
- 终端 cwd 跟随当前仓库的工作树，可以切换；
- 跨仓库任务可以分别提交；不能跨仓库原子提交；
- 分支唯一性按仓库判断。

**GIT-019 `[确认]` 空仓库**  
空仓库（还没有第一次提交）也需要支持。  
在产生第一次提交之前不创建会话工作树；会话在主工作树中工作。  
第一次提交由 Agent 在用户明确指令下发起，提交信息由用户确认或编辑；第一次提交后，工作树可以加入会话（Q9）。

**GIT-020 `[确认]` 已有工作树**  
已有 linked worktree 需要被发现、显示和切换。  
对 Agent/会话只读：Agent 不能写入，也不能自动 stash/删除；用户仍可在编辑器中手动编辑。  
主工作树不是“已有 linked worktree”，按 GIT-010 处理。  
如果某个分支已经被已有工作树检出，新会话不能再次检出同一分支。

### 4.3 Git 优先与提交

**GIT-025 `[确认]` 改动必须进入 git diff**  
对 Git 仓库中已跟踪文件的修改，必须直接写入工作树，并且能在 `git diff` 中看到。  
“Git 优先”指改动必须在 Git 可见、可归属、可提交的上下文中发生，不要求通过 `git apply` 或 Git 命令来编辑文件。

**GIT-026 `[确认]` 不自动提交**  
Agent 不自动提交。提交由用户审核 diff 后手动执行；只有用户明确要求时，Agent 才执行提交。

**GIT-027 `[确认]` 绕过 Git 的条件**  
允许绕过 Git 的情形：

1. 用户明确要求直接修改；
2. Agent 提出绕过 Git 的建议，用户在对话中同意。

授权通过对话完成，不弹出审核窗口。  
“绕过 Git”指：不创建分支/工作树、不要求改动出现在 git diff、直接写文件。

**GIT-028 `[确认]` 非 Git 仓库**  
非 Git 仓库允许直接编辑文件，不要求初始化 Git，不创建分支/工作树。

**GIT-029 `[推断]` Git 忽略/二进制/大文件**  
Git 忽略的文件、二进制文件、大文件、工作树外文件允许直接写入。这些改动不会出现在 `git diff` 中，但必须出现在工作区变更视图中，并标明“未纳入 Git”。

**GIT-030 `[确认]` 串行提交**  
一个会话同一时间只处理一个提交；提交完成后可以继续下一个提交，顺序产生多个提交（Q1）。  
提交信息由用户确认或编辑。

**GIT-031 `[确认]` 提交按仓库独立**  
一个提交只属于一个仓库；跨仓库任务需要分别提交；不能把多个仓库的改动放进同一个提交。

### 4.4 Git 视图

**GIT-035 `[确认]` 独立的只读 Git 视图**  
提供独立于聊天面板的 Git 视图，功能参考 VS Code 的 GitLens 插件。

**GIT-036 `[确认]` 视图内容**  
至少显示：

- 本地分支、远程分支；
- tags、stashes、worktrees；
- 每个分支的提交历史；
- 当前工作树状态；
- 未提交改动（staged / unstaged / untracked），默认显示所有工作树并可按仓库/会话/工作树过滤。

**GIT-037 `[确认]` 提交详情与比较**  
支持：

- 提交详情：作者、时间、消息、文件列表、逐文件 diff；
- 按分支、作者、时间、消息搜索/过滤；
- 分支之间、提交之间的比较；
- 文件历史/行历史（对应 GitLens 的能力，具体深度待设计）。

**GIT-038 `[确认]` 远程与 CI 状态**  
显示远程 ahead/behind、PR/MR 状态、CI 状态。  
PR/MR 和 CI 先只支持 GitHub；其他平台或未配置远程时显示“不可用”，不阻塞本地 Git 操作。

**GIT-039 `[确认]` 视图只读**  
Git 视图不提供 checkout、merge、rebase、cherry-pick、revert、tag、删除分支等写操作。写操作通过 Agent、会话分支控制或提交 UI 完成。

**GIT-040 `[确认]` 不在图中显示会话标记**  
Git 视图不需要显示“哪个分支属于哪个会话”或“每个工作树的 HEAD”标记。  
会话当前分支在工作区/会话 UI 中显示（见 GIT-074）。

**GIT-041 `[推断]` 大仓库性能**  
大仓库（几千/几万提交）必须支持分页、过滤、搜索，不能因加载全部历史而卡死。默认加载范围待设计。

**GIT-042 `[确认]` 多仓库视图**  
Git 视图支持多仓库：可以按仓库切换，也可以汇总显示所有参与仓库；每个仓库独立显示分支、提交、worktrees 和远程状态。

### 4.5 Agent Git 能力与授权

**GIT-045 `[推断]` 完整 Git 能力**  
Agent 具备以下能力（在用户允许时）：

- 读取：status、diff、log、show、blame、branch list、remote list、stash list；
- 本地写：add、commit、amend、branch create/switch/delete、merge、rebase、cherry-pick、revert、reset、clean、stash、tag；
- 远程：fetch、pull、push、force push、push 到任意分支（含 main）；
- 其他：submodule、LFS（不在会话工作流支持范围内，见 GIT-068）；PR/MR 创建属于平台能力，暂不纳入。

**GIT-046 `[确认]` 无独立 Git 审核弹窗**  
Git 操作不引入独立的 Git 审核弹窗。授权方式：会话模式 + 对话中的明确指令。  
用户在对话中要求“提交/合并/推送/切分支”等，即视为授权对应操作。  
ask 模式下，merge/reset/clean/restore/checkout -- <path> 等会覆盖或丢弃文件改动的 Git 操作使用现有审批弹窗；commit、push、创建/切换分支不弹（切换分支的脏改动按 GIT-014 询问）；auto 模式不弹；readonly/plan 禁止 Git 写操作。

**GIT-047 `[确认]` auto 模式无额外审批**  
auto 模式下 Git 操作不需要审批。readonly/plan 模式禁止 Git 写操作。

**GIT-048 `[确认]` 提交身份**  
提交使用用户自己的 Git 身份。  
`[推断]` 默认不添加 Co-Authored-By；签名、hooks 遵循用户 Git 配置。

**GIT-049 `[推断]` 凭据**  
使用系统 Git 凭据（SSH agent / credential manager）。应用不保存、不记录、不向模型暴露凭据。

**GIT-050 `[确认]` 不额外限制**  
应用不额外设置保护分支、force push 禁令或 PR 强制。push/force/目标分支由用户指令和仓库配置决定。  
风险提示：force push 和直接 push main 可能覆盖远程历史；应用不额外拦截，但必须在结果中明确反馈。

**GIT-051 `[推断]` 结果反馈**  
所有 Git 操作的结果（成功、失败、冲突、推送拒绝、认证失败）必须反馈到会话和 Git 视图，并给出可操作原因。

**GIT-052 `[确认]` 外部 Git 操作**  
外部终端的 Git 操作不主动同步到应用内会话状态；应用刷新显示并警告外部变化。  
如果外部变化影响 Agent 正在执行的操作（例如 HEAD 变了、分支被切走、文件被改），Agent 必须能检测到变化并停止当前操作，报告发生了什么（Q10）。

### 4.6 合并与集成

**GIT-055 `[确认]` 合并目标**  
默认合并回当前仓库的基分支；用户指定时合并到指定分支。  
多仓库时，合并目标按仓库分别确定。  
如果目标分支有未提交改动或已被其他工作树检出，Agent 必须先询问用户，不自动合并。

**GIT-056 `[确认]` 合并执行者**  
Agent 和用户都可以执行合并；大部分情况下由 Agent 执行（Q5）。

**GIT-057 `[确认]` 多会话合并串行**  
多个会话同时合并到同一仓库的同一目标分支时，必须串行排队，不能并发合并。  
不同仓库的合并互不影响。

**GIT-058 `[确认]` 冲突处理**  
合并冲突必须由 Agent 在对话中主动询问用户如何解决；不提供冲突审核 UI/弹窗（Q5）。  
不能静默选择一方。

**GIT-059 `[确认]` 合并后保留**  
合并后不自动删除分支或提交；工作树是否保留按 GIT-015/GIT-017 处理。

**GIT-060 `[确认]` 合并策略**  
默认使用 **merge commit**（保留会话分支的提交序列，目标分支上产生一个合并提交）。  
除非用户明确指定，Agent 不擅自使用 squash 或 rebase；用户指定时可以按指定策略执行（Q5）。

### 4.7 非 Git 与边缘场景

**GIT-065 `[确认]` 非 Git 工作区**  
直接编辑文件；不创建分支/工作树；Git 视图显示“非 Git 仓库”。

**GIT-066 `[推断]` 忽略/二进制/大文件**  
直接写入；变更在工作区变更视图中可见，但不在 `git diff` 中；不阻塞任务。

**GIT-067 `[确认]` detached HEAD**  
detached HEAD 下没有当前分支名。  
默认行为：从当前提交创建一个新的会话分支（按会话分支命名规则），然后在该分支上继续工作；如果创建失败，询问用户（Q9）。

**GIT-068 `[确认]` 子模块 / LFS 不支持**  
子模块和 LFS 不作为本功能的支持范围（Q9）。

- 子模块：父仓库只记录子模块的提交指针；应用不递归管理子模块内的 Git 操作，子模块内的改动不纳入会话分支的提交。
- LFS：应用不做专门支持；需要用户本机安装 git-lfs，diff/恢复可能只看到指针文件。

打开包含子模块/LFS 的仓库时，按普通文件处理，不保证完整的 Git 语义。

### 4.8 交互与终端

**GIT-070 `[确认]` 不新增独立 Git 审核窗**  
Git 业务操作不新增独立的 Git 审核弹窗。  
auto 模式不弹；ask 模式下 merge/reset/clean/restore/checkout -- <path> 等会覆盖或丢弃文件改动的 Git 操作使用现有审批弹窗；commit、push、创建/切换分支不弹（切换分支的脏改动按 GIT-014 询问）；readonly/plan 禁止 Git 写操作。  
Git 业务操作通过专用 Git 能力执行，不触发命令审批；授权由会话模式和对话指令决定。

**GIT-071 `[确认]` 文件写入与权限申请保留弹窗**  
文件写入/命令执行的现有审批机制保留；操作系统的权限申请也保留。  
ask 模式下，merge/reset/clean/restore/checkout -- <path> 等会覆盖或丢弃文件改动的 Git 操作也走现有审批；commit、push、创建/切换分支不弹（Q12）。

**GIT-072 `[推断]` 操作说明**  
Agent 在执行 Git 写操作前，应在对话中说明将要执行的操作和目标；用户可以在执行前打断或拒绝。该说明不是审核弹窗。

**GIT-073 `[推断]` 非阻塞反馈**  
提交、合并、推送的进度和结果以非阻塞方式显示；失败必须给出可操作原因。

**GIT-074 `[确认]` 会话分支可见**  
会话列表、聊天头部或状态栏必须显示当前会话的：

- 已选择/已参与的仓库列表，并标记当前活动仓库；
- 每个仓库的当前分支（未创建时显示“未绑定”）；
- 每个仓库的基分支；
- 每个仓库的工作树；
- 未提交改动数量；
- ahead/behind（如可获取）。

**GIT-075 `[确认]` 终端归属**  
终端面板属于工作区；每个会话有独立的终端实例，默认 cwd 为当前仓库的工作树。  
Agent 在不同会话中使用各自的终端；会话同时持有多个仓库时，终端可以按仓库切换 cwd（Q11）。

**GIT-076 `[确认]` 会话切换**  
切换会话时，文件树、编辑器、终端、未保存编辑跟随当前会话；未保存编辑按会话保留。  
重启后按 GIT-077 恢复（Q10/Q11）。

**GIT-077 `[确认]` 重启恢复**  
应用重启后恢复：

- 会话 ↔ 多个仓库 ↔ 分支映射；
- stash 列表（按会话/仓库/分支标签恢复未提交改动）；
- 打开的编辑器文件；
- 终端历史/状态（如可恢复）。

工作树不恢复：按需重建。重建时自动 apply 该会话最新匹配的 stash（见 GIT-079）。未完成的 merge/rebase 不能跨退出恢复；处理方式见 GIT-015。

**GIT-078 `[确认]` 会话头部 Git 控件**  
会话头部/状态栏提供：

- 仓库选择器：自动扫描逻辑工作区下所有 Git 仓库（排除 `node_modules`、`.pi-workbench` 等）；只列出自动发现的仓库，不支持手动添加工作区外仓库；选中仓库后设为当前活动仓库，终端 cwd、文件视图、Agent 操作对象跟随。
- 分支切换器：列出当前仓库的本地分支和远程分支；选择远程分支时创建本地跟踪分支；脏改动按 GIT-014 处理。
- 提交框：作用于当前活动仓库；提交该仓库的所有未提交改动（含未跟踪文件），提交前显示文件清单供审阅；提交信息由 Agent 预填，用户可编辑；不弹窗。

合并、推送通过对话执行。

**GIT-079 `[确认]` stash 自动恢复**  
重开会话/重启后重建工作树时，自动 apply 该会话最新的匹配 stash（按会话/仓库/分支标签）。  
apply 成功后 drop 该 stash；apply 冲突时保留 stash，提示用户处理。  
剩余的 stash（包括自动恢复冲突后的 stash、切换分支时产生的 stash）通过对话让 Agent apply/drop；Git 视图保持只读。  
切换分支时选择 stash 的改动不会在切回该分支时自动 apply，保留在 stash 列表，由用户/Agent 手动处理。

## 5. 验收场景

1. 两个写会话在同一仓库的不同分支修改同一文件，分别提交，依次合并，冲突在对话中询问并解决；多仓库场景同理。
2. 只读会话可以读取所有仓库的工作树和历史，但不能写。
3. 会话首次写操作前没有分支；首次写入后出现分支和工作树。
4. 首次写操作时当前工作树有未提交改动，改动被 stash+apply 到新工作树，原工作树干净。
5. 工作区文件视图显示所有参与仓库和工作树外文件；切换仓库/工作树能看到其他版本。
6. 会话 UI 显示参与的仓库、每个仓库的当前分支（或“未绑定”）；Git 视图显示分支、提交、diff、ahead/behind、PR/CI。
7. 切换分支时有未提交改动，Agent 在对话中询问；选择提交/stash/放弃/取消都能正确执行。
8. 用户与 Agent 在同一工作树同时改同一文件，冲突被检测并提示，不静默覆盖。
9. 非 Git 工作区直接编辑，不创建分支/工作树。
10. 忽略/二进制文件的改动在工作区变更视图中可见，但不在 git diff。
11. 会话结束（含关闭工作区/退出）：保留分支/提交，未提交改动自动 stash 保留，删除本会话创建的工作树，不自动清理分支；其他会话可接管分支。
12. 合并默认使用 merge commit；合并后不自动清理；多会话合并同一目标分支时串行排队。
13. 多仓库并行：一个会话同时持有两个仓库的工作树，分别提交；文件视图/Git 视图可切换或汇总；终端 cwd 跟随当前仓库。
14. 空仓库：第一次提交前在主工作树工作；Agent 在用户明确指令下创建第一次提交；提交后可创建工作树。
15. 已有工作树：可发现、显示、切换、编辑；不会被自动删除；分支不能被重复检出。
16. detached HEAD：从当前提交创建新的会话分支并继续工作。
17. 包含子模块/LFS 的仓库：按普通文件处理，不保证完整 Git 语义。
18. 应用重启后，会话、多个仓库、分支、stash、编辑器、终端历史按约定恢复；工作树按需重建；未完成合并/变基的处理见 GIT-015。
19. 关闭/退出时正在 merge/rebase：默认阻止；选择“中止操作并关闭”后先 abort，再 stash + 删除工作树；选择“取消”则保持现场。
20. 仓库选择器自动发现工作区下的 Git 仓库（不支持手动添加工作区外仓库）；选中后切换活动仓库；分支选择器选择远程分支时创建本地跟踪分支；提交框提交当前活动仓库所有未提交改动（含未跟踪），并预填 Agent 生成的提交信息。
21. 重开会话时自动 apply 最新匹配 stash；成功后 stash 被 drop；冲突时保留并提示。
22. 已有 linked worktree：Agent 写入被拒绝，用户可手动编辑；会话结束不自动 stash/删除。
19. Agent 执行 push/force/reset 等操作时，不出现独立审核弹窗；只有文件写入/权限申请才弹窗。
20. 外部终端改变 Git 状态并影响 Agent 操作时，Agent 检测到并停止、报告。

## 10. 工作树与依赖方案

> 固定工作树池提案已放弃（2026-10-26）。改为按需创建工作树，不预创建池、不设数量上下限；依赖采用 pnpm store + 硬链接。

### 10.1 已确认

- 每个写会话在首次写某个仓库时，按需创建一个 linked worktree 和会话分支；不预创建固定池。
- 工作树数量不设上下限（实际受同时运行的写会话数影响）。
- 工作树放在工作区 `.pi-workbench/worktrees/` 下；从文件树、文件监听和主仓库 Git status 中排除。
- 主工作树永不删除。
- 已有 linked worktree 对 Agent/会话只读，不自动 stash、不删除；用户可在编辑器中手动编辑。主工作树按 GIT-010 处理。
- 依赖：每个工作树独立安装，pnpm store + 硬链接去重；不 symlink 整棵 `node_modules`；setup 脚本在创建/首次使用时运行；清理构建产物，保留依赖。详见 10.4。

### 10.2 已确认：关闭/退出时的未完成 Git 操作

如果本会话创建的工作树存在未完成的 merge/rebase（包括 cherry-pick/revert 中断状态）：

- 默认阻止关闭/退出。
- 使用现有会话关闭确认，提示“有未完成的合并/变基，关闭会丢失进度”，提供“中止操作并关闭”和“取消”。
- 选择中止：先 abort，再 stash 已跟踪+未跟踪改动，最后删除工作树。
- 选择取消：保持会话和工作树不变。
- 不使用独立的 Git 审核弹窗，不保留工作树作为例外。

**其他已确认**：

- 会话结束包括关闭会话标签、删除会话、关闭工作区标签、退出应用；崩溃按异常处理。
- 关闭/退出时：stash 本会话创建的工作树的已跟踪+未跟踪改动；删除该工作树；已有工作树不自动 stash、不删除；stash 失败则不删。
- 崩溃/异常退出自动清理 orphan 工作树；未提交改动可能丢失；已生成的 stash/commit 保留。
- 重启恢复会话/分支/stash/编辑器/终端历史；工作树按需重建。
- 删除工作树前，如果存在未保存的编辑器内容或运行中的终端进程，沿用现有会话关闭确认；确认后才 stash + 删除，取消则不删。
- ask 模式：merge/checkout/reset/clean 等会改文件的 Git 操作走现有审批弹窗；commit、push、创建/切换分支不弹；auto 不弹；readonly/plan 禁止写。

### 10.3 已放弃：固定工作树池

原提案（固定 N 个槽位、永不删除、分配/归还）已放弃。原因：按需创建更简单；依赖通过 pnpm store + 硬链接去重后，不需要靠固定槽位控制磁盘。相关影响不再适用。

### 10.4 依赖方案（已确认，2026-10-26）

采用主流方案：每个工作树独立安装依赖，依赖包由包管理器的内容寻址存储去重；不共享整棵 `node_modules`。

**DEP-001 `[确认]` 依赖按工作树独立安装**

- 每个工作树独立安装依赖；不把 `node_modules` 整棵 symlink 到其他工作树。
- Node：优先 pnpm 的全局 store + 硬链接；bun 使用 clonefile/hardlink；npm/yarn 只共享缓存，`node_modules` 仍按工作树安装。
- Python：uv 缓存 + 每工作树虚拟环境；其他生态使用对应全局缓存。
- pnpm store 必须与工作树在同一文件系统；否则会退化为复制。

**DEP-002 `[确认]` setup 脚本**

- 创建或首次使用工作树时运行 setup 脚本：`pnpm install --frozen-lockfile` / `bun install --frozen-lockfile` / `uv sync`（按项目实际）。
- lockfile 变化时在该工作树重新安装；不要跨不同 lockfile 共享依赖目录。
- 不可再生的 gitignored 文件（`.env`、本地配置）从主工作树复制；`node_modules`、`dist`、缓存不复制。

**DEP-003 `[确认]` 清理与磁盘**

- 删除工作树前清理构建产物（`dist`、`.next`、`target` 等）；依赖随工作树删除。
- 如果工作树保留，清理构建产物但保留依赖目录。
- pnpm store 保留；下次创建工作树时安装从 store 硬链接，速度接近复用。
- 工作树数量按需创建，依赖占用随工作树数量增长；pnpm store 去重后主要占用是目录/元数据。
- 如需进一步省盘，可按 lockfile 哈希共享 `node_modules` + junction，但这是次选，不作为默认。

**主流参考**：

- Cursor：`.cursor/worktrees.json` 跑 `pnpm install`/`bun install`，官方明确不建议 symlink 依赖。
- Codex：`.codex` setup 脚本 + `.worktreeinclude` 处理 `.env` 等文件。
- Claude Code：`.worktreeinclude` 复制 gitignored 文件；提供 `worktree.symlinkDirectories`，但 pnpm/monorepo 场景不建议 symlink。
- OpenHands：把依赖预烘焙进 sandbox 镜像，并对停止会话回收 `node_modules`/`.venv`，恢复时再装。
